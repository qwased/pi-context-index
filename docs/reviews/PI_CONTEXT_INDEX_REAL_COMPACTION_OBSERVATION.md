# 真实会话两轮压缩观察：胶囊密度、codemode 默认字段与 W 候选

- 日期：2026-11-02
- 性质：真实任务试用（首次）观察记录，兼外审输入；不是设计修订，不是缺陷修复记录。本次未改代码、测试或设计。
- 样本：一次真实会话的两次手动压缩（同一天，间隔约 2 分钟），Pi 1.4.0，插件默认设置（`viewMaxChars=12,000`、`keep=1`、窗口 600,000）。两次 `tokensBefore` 都远低于窗口阈值，会话文件不记录 `reason`，因此只能从数值推断为手动压缩，不把它写成已证实的宿主原因。
- 数据边界：本文只保留角色、计数、字符长度、跨度和聚合指标；不保留会话正文、会话文件名、本机绝对路径、模型回答或可回放的会话记录。经用户授权，外审可在本地只读访问该真实会话（具体访问方式由提交者单独提供，不写入本文）；读取不改变边界：不得把会话正文、文件名、绝对路径或模型回答复制到文档、提交、发布物或外传。文中的“结论”是观察和修复建议，不是设计裁决。
- 一句话：**链路通过，胶囊待调。** S0 是 codemode 多段结果的默认字段取到 header；S1 是 W 只取最近两条，长结论 0 入选；S2 是连续压缩的非累积与恢复成本。
- 严重度：本文用 S0/S1/S2 表示观察建议的严重度（S0 = 建议 0.1.0 修；S1 = 需要设计修订/外审决定；S2 = 记录并继续观察），避免与实现阶段 P0–P5 混淆。

## 0. 结论摘要

| 级别 | 观察 | 证据（脱敏） | 建议 |
|---|---|---|---|
| S0 | codemode 工具结果有多段 text 时，默认字段取 `content/0` 的 header | 3/3 和 2/2 条 codemode `R` 行只显示 44–47 字符的 header；正文/错误在 `content/1`，长度 22–1,821 字符；默认 `read` 走同一字段 | 0.1.0 修字段选择；补两段 text 的合成夹具；提升 `SELECTOR_VERSION` |
| S1 | W 固定取最近两条非 live 助手文本，短过渡句会挤掉长结论 | 第一轮 6 段 ≥400 字助手文本（9,202 字）0 入选；第二轮 9 段（15,402 字）0 入选；预算只用 24.7%/27.1% | 设计修订候选：最近 2 条 + 空闲额度补一条实质性助手文本；不要只改常量 |
| S2 | 第二次压缩不继承第一次摘要；短期连续压缩不会让摘要更聪明 | 第二轮只净增 281 字符；上一轮的 W/N 被重选替换；设计上从全量历史重选 | 记录为设计取舍；在真实任务试用中继续观察 |
| S2 | 恢复成本与“当前状态”缺口 | 第一轮后 4 次 reader、18,627 字符；模型判定摘要只能恢复“做过什么”，不能恢复“做到哪里” | 维持“摘要 + reader”路径；当前状态是否入胶囊另议 |

级别是观察者的建议，不是外审结论；S0/S1 的最终修法见 §5、§6。

## 1. 指标与口径

### 1.1 样本

- 压缩 1：存档 120 条、live 15 条；`tokensBefore=173,074`；摘要 2,965 字符；预算 12,000。
- 压缩 2：存档 143 条、live 10 条；`tokensBefore=45,718`；摘要 3,246 字符；预算 12,000。
- 两次压缩之间只隔约 2 分钟；第二次的 `tokensBefore` 远低于窗口，也没有 threshold/overflow 的明显证据。

### 1.2 两轮总表

| 指标 | 第 1 轮 | 第 2 轮 |
|---|---|---|
| `tokensBefore` | 173,074 | 45,718 |
| 摘要长度 / 预算 | 2,965 / 12,000（24.7%） | 3,246 / 12,000（27.1%） |
| 存档 / 展示 span | 120 / 9 | 143 / 10 |
| live tail | 15 条 / 45,046 字符 | 10 条 / 7,526 字符 |
| 引用原文 / 摘要长度 | 460（15.5%） | 513（15.8%） |
| 非 live 用户原文覆盖 | 153/153（100%） | 190/190（100%） |
| 非 live ≥400 字助手文本 | 6 段 / 9,202 字，0 入选 | 9 段 / 15,402 字，0 入选 |

### 1.3 口径

- `tokensBefore` 是宿主的计数；摘要、tail 和引用字符是 UTF-16 长度。只有明确写“按 3 字符/token 估算”时才做 token 换算。
- “引用原文”是按 `details.shown` 的 `end-start` 求和；第二轮含 159 字符的嵌套 `error` 字段。其余字符是标签、地址、导航行和空行，导航本身有价值，因此不把 84% 都称为浪费。
- “≥400 字助手文本”指非 live、主文本字段长度 ≥400 的 assistant 消息；只算 text，不算 thinking。
- 计数自洽：第一轮 9 quoted + 95 index-only + 15 live = 119 effective；第二轮 9 + 122 + 10 = 141。

## 2. 链路与切点

### 2.1 做对了的部分

- **插件路径成立。** 两条 compaction 都是 `fromHook:true`，摘要格式是插件模板，没有模型摘要回退的痕迹。
- **没有孤立 toolResult。** 第一轮从 assistant 109 起，第二轮从 user 138 起；两者都是合法 tail 边界。
- **用户目标不丢。** 非 live 用户原文 100% 引用；首条目标和最近指令都在。
- **计数一致。** `quoted/indexOnly/live` 与 `effective` 守恒，见 §1.3。
- **reader 可用。** 第一轮后 4 次读取确实恢复了上下文，并写出了约 1.9k 字符的复盘；`details` 只带地址和跨度，没有复制正文。

### 2.2 第一轮切点的代价

第一轮没有切在最后一个 user 104，而是 assistant 109。按项目 3 字符/token 估算：

- 104–108 的 suffix 约 23.3k tokens，超过 16k 的 manual tail 上限；
- 109 起约 15.0k tokens，刚好装下；
- 15 条 tail 共 45,046 字符，其中约 33k 是工具调用参数（写文档的长脚本）。

切点合法，但最后一个用户指令只活在摘要里，live tail 从 assistant 开始。这是 tail 预算与超大 toolCall 参数的交互，不建议在 0.1.0 动；如果未来要改，方向是让超大参数不独占 tail 预算，但那会改变宿主上下文，风险高。

## 3. 发现

### 3.1 S0：codemode 多段结果默认取 header

真实 Pi 的 codemode 结果有两段 text：

1. `content/0`：`Script completed/failed … Output:`，44–47 字符；
2. `content/1`：真正的输出或错误，本样本里 22–1,821 字符。

[src/fields.ts](../../src/fields.ts#L256-L283) 的 `primaryFieldPath` 取“第一个 text block”；[src/observations.ts](../../src/observations.ts#L346-L362) 的 `observationResultField` 又沿用它。实际结果：

- 第一轮 3 条 codemode `R` 行全部是 44–47 字符的 header；实际错误正文 91/185 字符、命令结果 22 字符没有出现。
- 第二轮 2 条 codemode `R` 行是 header；另有 1 条嵌套 error（159 字符）是有效的。
- 不只是胶囊：[src/reader.ts](../../src/reader.ts#L125-L134) 的默认 `read e:<id>` 也走同一个字段，所以直接读也会先拿到 header。

按真实条目复算，`primaryFieldOf` 返回 `/message/content/0/text`；正文在 `/message/content/1/text`。这不是“索引不到正文”——字段迭代器仍枚举两段，显式 `field` 也能读到；问题是**默认字段和胶囊摘录选错了段落**。

影响边界：

- R1–R3 的“可索引、可按地址寻回”仍成立；
- 但“默认 read 给出主结果”和“W 引用最新错误/命令结果”不成立；
- 对 codemode 会话，用户需要先 `list ref` 才发现第二个字段，恢复路径变长。

测试缺口：现有 [tests/fields.test.ts](../../tests/fields.test.ts#L95-L132) 和 [tests/capsule.test.ts](../../tests/capsule.test.ts#L240-L300) 的 codemode 夹具都只有一个 text block（`text: "script output"` / 单段聚合输出），没有覆盖真实的两段形态。

### 3.2 S1：W 只取最近两条，长结论 0 入选

设计 §8.2 明确 W 是“最近两条非 live 助手文本”，[src/candidates.ts](../../src/candidates.ts#L735-L757) 用 `slice(-CAPSULE_W_ASSISTANTS)` 实现，常量在 [src/candidates.ts](../../src/candidates.ts#L29-L39)。本样本的后果：

- 第一轮选中的是 49/123 字符的两条过渡句；6 段 ≥400 字助手文本合计 9,202 字，0 入选。
- 第二轮选中的是 31/42 字符的两条过渡句；9 段长文本合计 15,402 字，0 入选。
- 再往前一条助手文本是第一轮 2,778 字符的调查结论；把它加进 W 仍远低于 12k 预算。

预算不是分配器没花：`buildCapsule` 已经把候选级别的所有升级走完，并做了 U→W→N 的借额（[src/render.ts](../../src/render.ts#L455-L498)）；`neededChars` 就是 2,965。要填满只能增加候选，不能改 `Bcap` 或份额。

设计张力：

- W=2 是设计选择，不是实现偏差；短助手说明也可以入选（设计 §8.2 最后一段）。
- 但“最近”不等于“有信息量”。在本样本里，最近两条恰好是过渡句，真正的结论在第三条；W=3 或“最近 2 条 + 空闲额度补一条实质性文本”都能在预算内解决。
- 改 W 需要设计修订和 `SELECTOR_VERSION` 提升，不能在 0.1.0 里悄悄改。

### 3.3 S2：连续压缩不累积

第二轮摘要只比第一轮多 281 字符（3,246 vs 2,965）。它按设计从全量有效历史重选，不引用上一份摘要；好处是不会“摘要的摘要”漂移，代价是上一轮已选中的 W/N 不会自动继承：

- 第一轮的两条助手工作说明被第二轮的两条新说明替换；
- 第二轮的结论型内容主要在 live tail 里，所以摘要看起来更薄；
- 下一次压缩才会把这次 live 的结论纳入非 live 候选，存在一轮延迟。

这不是实现 bug；它是“每次从全量历史重选”的直接结果。真实任务试用应记录这个延迟是否造成重复探索。

### 3.4 S2：恢复成本与状态缺口

第一轮压缩后，模型用了 4 次 reader，返回 18,627 字符（含框架），才写出约 1.9k 字符的复盘；成本约为摘要的 6.3 倍。第二轮的模型判定是：只能恢复“做过什么”，不能恢复“做到哪里”，并列出三项缺口：

1. 未落盘的设计判断；
2. 当前工作树状态；
3. 未决项与下一步。

这与数据一致：摘要里没有当前 `git status`，也没有 pending decisions。需要公平地说：第二轮的 live tail 保留了只读检查的 `git status`、目录和文档读取，所以**完整上下文并没有全丢**；但摘要本身没有这些。第一轮的 tail 只有一个小 status（3 个文件），不是全量。

### 3.5 切点小遗憾（不单独列为问题）

见 §2.2。切点合法；0.1.0 不建议改。

## 4. 对照设计 §13.2 的真实任务验收

设计 §13.2 要求压缩后检查四件事。本样本只能提供一次观察，不能替代三个真实任务试用：

| 验收项 | 本样本观察 | 判断 |
|---|---|---|
| agent 能否说清正在完成的用户要求并继续下一步 | 用户目标 100% 保留；但第二轮模型判定摘要不能恢复“做到哪里” | 目标保持通过；“继续下一步”未直接验证 |
| 能否找到早期具体数字、一条中段更正、一项近期未展开的工作说明 | reader 路径可用；摘要本身只给地址和导航 | 路径通过；摘要单独不足 |
| 原文找回需要几次调用，是否重复全文读取 | 第一轮 4 次 / 18.6k 字符；未见重复全文读取 | 可接受，但成本高于摘要 6.3 倍 |
| 与旧插件续接过程相比，是否减少重复解释/探索/执行 | 本样本没有旧插件对照 | 未验证 |

## 5. 修复选项

### 5.1 选项

| 选项 | 内容 | 0.1.0 | 风险 / 代价 |
|---|---|---|---|
| A（推荐） | 只修 S0：多段 toolResult 的默认字段；补测试；提升选择器版本 | 修 | 低；改变 `primaryField` 和 `shown`，需要 golden |
| B | A + W 预算感知（最近 2 条 + 空闲额度补一条 ≥400 字助手文本，或 W=3） | 外审后决定，可能放 0.2 | 中；改变候选集，需要设计修订、golden、基准 |
| C | 两者都推迟到 0.2 | 不修 | 默认 read 仍先返回 header；不建议 |

### 5.2 S0 的修法候选

1. **对 `toolResult` 选最长 text block（并列取后者）**：最通用；本样本会选 `content/1`。assistant 仍取第一个 text（避免选到长 thinking）。
2. **对 `toolResult` 选最后一个 text block**：适合“header + body”；但如果某工具是“body + footer”就不稳。
3. **按工具特判 codemode**：最小，但会把 Pi 的展示形态固化进插件；不推荐作为唯一规则。
4. **跳过明显的 header 行**：需要维护 boilerplate 列表；脆弱。

推荐 1，配一个 codemode 专用夹具；如果外审认为“最长”会误选长 JSON，再退到 1+3 的组合。

测试要求：

- 两段 text 的合成 codemode 结果：`primaryFieldPath` 应指向 `content/1`；`read` 无 `field` 时返回正文；胶囊 `R` 行显示正文/错误而不是 header。
- 单段 toolResult、assistant（thinking + text）、user 字符串的既有行为不变。
- 两段中第二段更短时，要明确规则（最长 vs 最后）并锁死；不要用“看起来像 header”的模糊判断。
- `SELECTOR_VERSION` 提升；更新 capsule golden 和 `details.shown` 断言。

### 5.3 S1 的修法候选

1. `CAPSULE_W_ASSISTANTS=3`：最小；本样本能纳入 2,778 字符结论，但按“最近”选可能选到长推理而不是结论。
2. 最近 2 条 + 空闲额度下最近一条 ≥400 字助手文本：更符合“预算感知”，但引入新的候选顺序，需要设计修订。
3. 不改 W，只在真实任务试用中记录“结论 0 入选”的频率；如果多个样本重复出现，再改。

推荐先做 1 的离线实验（不改代码，用合成夹具比较字节和覆盖），把结果交给外审；如果收益稳定，再做 2。

### 5.4 版本与发布

- S0 是默认字段行为变化：提升 `SELECTOR_VERSION`，更新 capsule golden；如果 `primaryField` 也影响 reader 默认结果，在 CHANGELOG 写用户可见变化。
- S1 是候选集变化：必须同批更新设计 §8.2 与选择器版本；不要只改常量。
- 两者都不改变 LLM-free、单压缩路径、三个设置、无 summary-of-summary、无宿主拦截这些硬规则。

## 6. 外审问题

**Q1. S0 是否应按 bug 处理？** 设计只规定“工具结果文本可索引”，没有规定多段 text 的默认字段；实现选了第一段。默认 `read` 和胶囊 `R` 行都受影响。是 bug、是未规定的边界，还是可接受的产品选择？

**Q2. 如果修，规则选哪个？** 最长、最后、跳过 header，还是 codemode 特判？对 assistant（thinking + text）、单段结果、长短两段、JSON 正文分别是什么行为？需要哪些测试？

**Q3. S1 是否值得在 0.1.0 改？** 本样本只有一次；6/9 段长助手文本 0 入选，但 W=2 是设计明文。是设计缺陷、调参项，还是需要更多真实样本才能判断？如果改，选 W=3 还是预算感知的额外候选？

**Q4. 0.1.0 是否应阻塞？** S0 影响默认 read；S1 影响胶囊信息量。两者分别应标为设计阻断、实现阻断还是非阻断？发布说明怎么写？

**Q5. 测试和证据最低要求是什么？** 两段 text 的合成夹具够不够？要不要一个真实 codemode 会话的脱敏指标、一个同规模真实任务、或一次旧插件对照？如何避免用单样本外推？

**Q6. 有没有更根本的替代方案？** 例如让 reader 默认返回“所有 text 段的有界拼接”、让 W 按信息量而非时间选、或把“当前状态”从摘要彻底交给 reader。哪些会破坏“有限视图 + 精确地址”的设计？

## 7. 合成复现

### 7.1 codemode 两段结果

构造一个合成条目（不是真实会话）：

```json
{
  "type": "message",
  "message": {
    "role": "toolResult",
    "toolName": "codemode",
    "content": [
      { "type": "text", "text": "Script completed\nWall time 0.0 seconds\nOutput:\n" },
      { "type": "text", "text": "ACTUAL OUTPUT\n" }
    ]
  }
}
```

当前 `primaryFieldPath` 应返回 `/message/content/0/text`；期望返回 `/message/content/1/text`。把同一形状放进 `tests/fields.test.ts` 和 `tests/capsule.test.ts`，即可在不使用真实会话的情况下复现。

### 7.2 W 候选

构造三段非 live 助手文本：两条 50 字符的近期过渡句，再加一条 2,778 字符的结论；上下文其余部分保持短。用 12k 预算构建胶囊，观察：

- 当前 W=2：两条过渡句入选，结论 0 入选，摘要约 3k；
- W=3：结论入选，摘要约 5.7k，仍在 12k 内；
- 预算感知额外候选：结论入选，且不改变“最近 2 条”的优先顺序。
