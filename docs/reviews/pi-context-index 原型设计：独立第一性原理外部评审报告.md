# **0\. 第一性原理结论（优先于六问）**

## **0.1 问题重述与作用层判断：问题是否成立、压缩是不是正确的作用层？**

### **证据支持的结论**

* **传统语义摘要的"不可核对、覆盖不可见与状态伪造"问题在实测中真实存在且后果显著**：  
  * 在 `docs/plans/PI_CONTEXT_INDEX_PROTOTYPE_DESIGN.md` §12.3 主表（对应 `research/prototype/out/experiment-summary-rescored.json`）中，旧基线 `0.1.5 @6,287` 与 `0.1.5 @9,583` 在最早测试记录（`422 pass / 0 fail`）上得分均为 `0/3`，测试计数向量得分仅为 `1.0/3`，71 个唯一操作路径仅列出 `16/71`（`@6,287`）与 `57/71`（`@9,583`），对覆盖范围问题（`earliest_saved`、`indexOnly`、`view`）全部为 `0/3` 或 `3/3 null`。  
  * 相比之下，`pi-context-index` 新视图在 `7,096 chars`（`@8,217` 预算档，因 `needed` 截止与 `7,850`/`9,583`/`12,560` 逐字相同，见设计 §5.4、§12.2）下，将最早测试提升至 `3/3`、计数向量提升至 `3.0/3`、唯一操作路径提升至 `71/71`、覆盖核对提升至 `3/3`。  
  * 在 `§12.3` 变体表中，当覆盖行去掉保存区间或未展示计数时（`新视图，旧覆盖头` 与 `新视图，无覆盖头`），模型对 `indexOnly/view` 或 `earliest` 的回答立即退化为 `0/2`（乱猜非 null 值或漏答 `#0`）；当计数行去掉数值只留引用（`只给引用`）或去掉计数行（`无计数行`）时，最早测试跌回 `0/2`、向量跌回 `1.0/2`。这直接证明**结构化目录边界与"值 \+ 引用"台账在压缩产物中具有不可替代的承重作用**。  
* **结构可达（Reachability）与模型行为成败（Behavioral Success）存在显著断层**：  
  * 设计 §12.5 聚焦实验表明，即便首条消息的 6 个计分约束在视图文本中 `6/6` 字面存在（`u-full`、`新视图 @8,217`、`0.1.5 @9,583`），模型每次也仅抽出 `3–4` 个（均值 `3.0–3.5/6`）。  
  * 设计 §12.7–§12.9 表明，当用户消息被头尾行摘录截断、且可见头部的规则在语法上看似自洽完整（如 `T6` 可见行写"测试通过后即可直接记录 changelog"，而隐藏中段写"单次 green run 绝不足够，必须独立重跑"）时，模型在无提示条件 `A` 下出现高比例零调用直接答错（§12.8 合并 `7/9` 零调用答错；§12.7 `2/3`；§12.9 `1/3`），即便在给出正向规则 \+ `cover` 地址的 `C5` 下仍有 `2/9` 不调用 `cover` 而直接失败（`research/prototype/out/render5-summary.json`）。

### **独立设计判断**

* **问题完全成立，但"压缩（Compaction）"只能解决"历史可追溯性（Provenance & Addressable Storage）"，不能独自充当"工作连续性（Task Continuity）"的唯一载体**：  
  * 宿主的 `session_before_compact` 钩子本质上是**上下文窗口的垃圾回收器（Context GC）**。传统方案的错误在于让 GC 顺便扮演"项目经理"（生成目标、待办、当前状态与撤销关系）；本设计清醒地剥离了这一职责（设计 §1.3、§1.5），将压缩器收敛为**确定性档案管理员（Archivist）**。  
  * 然而，当压缩器只做"档案管理员"并对超长用户指令执行**头尾行截录（U0 2+2 行或 10+9 行）时，它无意中制造了本原型最核心的失败模式："表面完备的误导性摘录（Deceptive Excerpt Completeness）"**。  
* **五大失败维度的优先级排序**：  
  * **第一优先级：正确性与信任失败（局部摘录诱导的假阳性作答）**。如果一条记录完全 `IndexOnly`，模型知道自己没看到正文；但如果一条 39K 的指令被展示了前 9 行和后 9 行，且前 9 行恰好有一句看似完整的肯定规则，模型就会把"部分摘录"当成"完整规则"直接作答（`zeroCallWrong`）。这是比"检索多花一轮"严重得多的正确性风险。  
  * **第二优先级：成本倒挂风险（Deep-Read Cost Inversion）**。在 `37K` 跨度上，一次 `cover` 返回 `37,615 chars`，加上视图 `6,177 chars` 共约 `43.8K chars`，已经超过被压缩前的整条原始消息 `39,324 chars`（设计 §12.9）。如果深跨度频繁被 `cover` 全量拉回，压缩不仅不省 token，反而净亏一个视图开销。  
  * **第三优先级：可用性与触发落差（Trigger & Continuation Gap）**。模型不主动跟 `next` 翻页（§12.8 长跨度 `0/24` 跟随 `next`），必须依赖服务端合并读取或更紧凑的两阶段导航。  
  * **第四优先级：宿主与跨分支一致性（Host & Fork Integrity）**。同文件追加已闭环，但跨文件 fork、运行中取消与真实自动压缩闭环尚未验证。  
  * **第五优先级：隐私边界（Privacy Enforcement）**。确定性 ID/路径排除已一致，但自由文本中的秘密仍依赖外部脱敏或显式标记。

## **0.2 设计理念的承重部分与偶然约束剖析**

**独立重述本设计理念**：会话压缩不应产出不可核对的 LLM 叙事，而应通过纯确定性算法产出三元组——**(1) 守恒的双层身份目录（`I = E ⊎ X`，`E = Live ⊎ Quoted ⊎ IndexOnly ⊎ Unavailable`）**、**(2) 按真实候选成本 `needed` 封顶的精确源子串展示视图**、以及 **(3) 绑定同一快照与隐私策略的字段/偏移级只读寻址器（Reader）**。

| 设计命题要素 | 承重判定 | 第一性原理分析（去掉或改变后会发生什么？） |
| :---- | :---- | :---- |
| **1\. 双层分母 `I/E/X` 与四状态互斥分区（`unaccounted=0`）** | **核心承重（不可妥协）** | 若去掉，读者无法区分"从未发生""被分支/编辑排除（`X`）""已保存未展示（`IndexOnly`）"与"源损坏（`Unavailable`）"，整个可核对性大厦直接坍塌。 |
| **2\. 零模型调用与确定性构建** | **核心承重（不可妥协）** | 保证了压缩延迟在毫秒级（470 条 7–8ms，10k 条 133–218ms）、零压缩期 token 消耗、零摘要幻觉、以及相同输入下的逐字节可重放性（`invariants.mjs` 18/18）。若允许模型参与压缩，将破坏确定性、重引入状态幻觉并使每次压缩耗时数秒至数十秒。 |
| **3\. 不生成目标/待办/当前状态/撤销关系** | **核心承重（职责边界正确）** | 时间顺序只证明先后，不证明语义覆盖（`supersedes`）。把动态任务状态交给外部持久文件（形态 B 的 `task-book.md`）或独立状态插件，是消除过期状态污染的唯一干净解法。 |
| **4\. 预算按 `needed` 截止（`B = min(Bcap, needed)`）** | **核心承重（机制精良）** | 打破了"给多少预算就凑多少字"的潜规则，证明了放开上限（至 4,000 tokens / 12,560 chars）与控制实际体积（7,096 chars）可以兼得（设计 §5.4）。 |
| **5\. 台账"值 \+ 引用"与 Reader"字段 \+ UTF-16 偏移 \+ 快照守卫"** | **核心承重（实证必需）** | 实验已证明只给引用不给值（§12.3 变体表 `0/2`）或只给行号不给字节偏移（§12.6 T5/C 失败、§12.5 旧式 reader 偏移 `0/3`）会导致严重退化。 |
| **6\. 对超长用户消息默认做"头尾行摘录（U0）"** | **历史/偶然选择（存在结构缺陷，需修正）** | 作者沿用了"每条用户消息先给头尾几行（U0）"的惯例。但当消息包含长篇规则且中段有例外/反转时，头尾摘录比 `IndexOnly` 更易诱导模型盲目自信。应允许对超长消息采用"结构大纲/首行签名 \+ 显式未完门控"替代机械头尾摘录。 |
| **7\. 完全拒绝隐藏跨度内的确定性词法路标，改用 1,200 字符固定网格页表（`pages@`）** | **历史/偶然约束（已被实证证伪，应删除）** | 作者为避免"关键词寻找禁令"的不可复现性，走向了另一个极端：只打印毫无语义的 1,200 字符固定字节网格页表（`render-3`）。结果在 §12.8 和 §12.9 所有运行中，页表与 `page`/`line` 参数被调用 **0 次**（`usedPage=0`）。相反，提取隐藏跨度中的确定性结构标题（如 Markdown `#` 标题行或编号章节偏移）同样是 100% 确定性、零模型调用的，却能提供真正的导航价值。 |
| **8\. 在时间线对所有 `span > 12,000` 同时打印 `max` 与 `cover` 全量调用** | **演进补丁（过度耦合，需重构）** | `render-5` 为解决 `37K` 的多窗口断层，在 `U` 行同时塞入 `max` 和 `cover` 两个长 JSON 调用，既挤掉了 `t6`/`t6l` 的一行原文（隐藏跨度 \+86 chars），又导致 `15K` 跨度上 `C5` 9/9 盲目调用 `cover`（工具字符 \+12%）。 |

## **0.4 替代架构方案比较（4 个方向深度对比）**

为了避免只与"更差的传统摘要"作稻草人对比，下表将本设计当前形态（方案 1）与三种具有竞争力的替代/演进架构（方案 2、3、4）在六个核心维度上进行横向评估：

## **0.5 保留 / 修改 / 重构 / 替换建议（Keep / Modify / Refactor / Replace）**

基于第一性原理与实证数据，本评审**不建议推翻重来（No Replace）**，也不接受"原封不动照搬 render-5（No Blind Keep）"，而是给出明确的 Keep \+ Modify \+ Refactor/Delete 路线图：

* **Keep（原样保留的核心资产）**：  
  * 保留独立插件 `pi-context-index` 定位、零模型调用、不兼容/不迁移 `0.1.5` 旧格式、不落权威 sidecar 的架构决定（设计 §0、§3.5）。  
  * 保留 `I/E/X` 双层分母、`E = Live ⊎ Quoted ⊎ IndexOnly ⊎ Unavailable` 互斥四状态（`unaccounted=0`）、字段级 `shown ⊎ hidden ⊎ policyExcluded` 分区与 18 项结构不变式（设计 §2、§3.2）。  
  * 保留顶部覆盖行格式（必须包含 `saved=#0-#M` 区间、各状态计数、`X` 原因与 `view` 入口）及预算公式 `B = min(Bcap, neededChars)` 与候选支付顺序 `H → U0 → EC → O → U1 → A`（设计 §5、§6.1）。  
  * 保留台账"值 \+ 引用"最低形态、模板禁用状态断言词但逐字引用允许（按来源区分断言与引用，设计 §1.6、§15.2）。  
  * 保留 Reader 的 5 个基础动作（`view` / `read` / `range` / `scan` / `touched`）、单动作 schema、`viewId` 快照校验、以及"跨文件 fork 无权威映射即拒绝旧引用"的 fail-closed 原则（设计 §3.3、§7）。  
* **Modify（必须在设计契约中修改的机制与默认值）**：  
  * **修改 `cover` 的打印门与触发条件（解决 Q3/Q4 的 15K 冗余与成本倒挂）**：废止"只要 `span > readMax (12,000)` 就在时间线并列打印 `max` 和 `cover`"的规则。改为**阶梯式门控（Two-Tier Gate）**：  
    * 当 `1,200 < span <= 24,000`（即 1–2 个 `readMax` 窗口，如 `15K` 的 `t6`）时，时间线 `U` 行**只打印 `max`（12,000 chars），不打印 `cover`**；若模型调用 `max` 后仍有 `unread > 0`（如 `t6` 剩余 `3,188 chars`），由 `read` 结果尾部的 `[next: ...]` 直接给出剩余区间的单次读完调用。这在零额外规则下即可消除 `15K` 上的 `cover` 冗余（避免 `C5` 多花 `+12%` 工具字符），同时保证 `t6` 目标在第一窗口内 `9/9` 命中。  
    * 仅当 `span > 24,000`（即 `windows >= 3`，如 `37K` 的 `t6l`）时，时间线才显式打印 `cover` 动作及总成本估算。  
  * **修改 `coverMax` 截断时的 `isError` 契约（解决 Q1 的错误语义混淆）**：当 `cover` 正常执行但因达到宿主策略上限 `coverMax` 而返回前 `coverMax` 字符 \+ `next` 游标时，**不得设置 `isError: true`**（当前设计 §7.4 与 `host-pi.mjs` 第 136 行设为 `isError: true`）。策略上限截断是预期内的分页边界（与 `read` 达到 `12,000` 返回 `next` 同构），不是执行错误；应返回 `isError: false`，通过结果头 `[PARTIAL COVER: covered/total chars]`、尾行 `[cover incomplete ... next: ...]` 及 `details.incomplete = true` 表达未读完。把正常分页标为 `isError: true` 违反工具成功/失败语义，且极易导致跨模型（尤其是严谨遵循 tool error 语义的模型）丢弃已返回的 20,000 字符有效正文。  
  * **修改 `U` 行内联地址格式以避免挤占原文行（解决 §12.9 的 \-86 chars 倒退）**：当前 `render-5` 在 `U #1` 内联打印完整的 `max: {"read":1,...}` 与 `cover: {"read":1,...}` 两个 JSON 字符串，导致 `t6` 和 `t6l` 各被挤掉第 10 行引用原文（`lines 1-10` 退化为 `lines 1-9`，隐藏跨度增加 `86 chars`）。应将内联地址压缩为单次参数模板（如 `read #1 field="content" offset=803 [max=12000 ~3822tok | cover=true ~11916tok]`）或将结构地址固定计入 `H` 预算配额，确保升级导航协议不会反过来缩减用户原文展示行数。  
* **Refactor / Delete（建议重构与直接删除的部件）**：  
  * **删除 `view` 中的 1,200 字符固定网格页表（`pages@889,2089,...`）以及 Reader 的 `page` 参数**：在 `§12.8` 与 `§12.9` 全部实验臂中，`usedPage = 0`（设计 §12.8 发现 4）。固定 1,200 字符切分既不对齐自然段也不携带标题信息，属于无行为收益的死协议；删除后可简化 `reader.mjs`、TypeBox schema 与测试面。保留 `offset`、`length`、`line`（对齐 U 行行号）与 `cover` 即可。  
  * **删除 `C2/D2` 分页提示词与 `D5` 的 `STRUCTURE` 行**：实验已证明 `C2` 覆盖率仅 `3/9` 且平均 prompt tokens 高达 `20,463`（对比 `C5` 的 `13,570`），`D5`（`5/9`）相比 `C5`（`7/9`）无正向增益（设计 §12.9 发现 3、4）。正式产品的 `promptGuidelines` 只保留精简后的 `C`（基础正向规则）+ 按需门控的 `COVER` 规则。  
  * **重构隐藏跨度提示（可选高价值增强）**：用零模型调用的确定性行首扫描，在 `U` 行隐藏跨度标记中附带最多 3 个非空章节标题/大纲锚点（如匹配 `/^(#{1,4}\s+.+|[A-Z][A-Za-z0-9 -]{2,30}:)/` 的行首子串及其精确偏移）。这不引入任何 LLM 语义评分，完全满足"精确源子串 \+ 偏移"契约，却能从根源上缓解 `T6` 的 `2/9` 不触发缺口。

* **当前证据足以支持的部分**：`I/E/X` 目录与四状态分区的数学完备性（18/18 不变式）、`needed` 预算截止机制、台账"值 \+ 引用"与 Reader"字段 \+ 偏移"相对于 `0.1.5` 的显著结构优势、以及 `cover` 在 `37K` 单夹具上相对于无 `cover` 的机械可达性突破（`C5` `7/9` vs `C` `0/9`）。

# **1\. 六个具体问题逐项裁定（Q1–Q6）**

## **Q1. 深跨度 `cover` 机制是否成立**

* **结论**：**有条件接受（Conditionally Accept）**  
* **依据**：  
  * **证据支持的结论**：  
    * 在 `37K` 长跨度夹具（`t6l`，隐藏跨度 `37,414 chars`、32 页、4 个 12K 窗口、目标偏移 `20,751`）上，`render-5` 的 `C5`（正向条件 \+ 覆盖规则）合并达到 `7/9` 正确、`7/9` grounded、`7/9` `targetCoveredByRead`、`7` 次调用 `cover` 全部成功且 `unread=0`，每次覆盖 `32/32` 页；而同视图无覆盖规则的 `C` 为 `0/9`，同帧 `render-3` 的 `C` 为 `0/9`，分页规则 `C2` 仅为 `3/9`（`docs/plans/PI_CONTEXT_INDEX_PROTOTYPE_DESIGN.md` §12.9 主结果表；`research/prototype/out/render5-summary.json` `combined` 行 `C5-positive-plus-cover`、`C-positive-conditional`、`C2-positive-plus-paging`）。  
    * 结构探针 `research/prototype/probe-render5.mjs`（8/8 通过，`out/probe-render5.json`）与宿主检查 `host-pi.mjs`（N2 端到端检查，`out/host-checks.json` 第 97、348 行）证实：`cover` 返回的 `37,414 chars` 正文严格等于源字段 `803-38217` 切片，结果头与成本行（`37,615 chars` 总结果）精确一致，且 `details` 仅包含结构元数据（`< 400 chars`），不复制长正文。  
  * **独立设计判断**：  
    * `cover` 在机制上解决了模型"不肯连续发 2–3 次 `next` 工具调用翻页"的行为瓶颈，且由于减少了多轮上下文重发，37K 上单次 `cover` 的累计 `promptTokens`（`14,208`）反而只有三次 `next`（`28,167–28,171`）的一半（设计 §12.9 成本账表）。  
    * 但当前契约存在两处概念冲突：一是把"视图有界（`6,287 chars`）"与"Reader 按需拉回长正文（最高 `48,000 chars`）"混在同一 `read` 动作下而未在契约总则中明确区分"静态视图有界"与"动态按需流式合并读取有界"；二是当 `cover` 遇到 `coverMax`（如 `20,000 chars`）截断时，将其标记为 `isError: true`（设计 §7.4、§12.9 及 `host-pi.mjs` 第 136 行），混淆了"工具执行失败"与"达到单次分页上限的正常截断"。  
* **要求的修改**：  
  * **修订设计 §1.2 与 §6.4 契约表述**：明确区分"压缩视图（Compaction View）严格受 `B = min(Bcap, needed)` 限制"与"Reader `cover` 是显式按需触发的跨窗口合并读取，受独立的单次/单回合读取预算 `coverMaxChars` 限制"。写入四条硬约束：**仅限模型显式按需调用、必须在地址与结果中打印整段字符/token 估算成本、严禁宿主在压缩或首轮自动预热（no auto-prefetch）、严禁在 `details`/日志/TUI 状态中复制 `cover` 正文**。  
  * **修订设计 §7.1 与 §7.4 的 `coverMax` 归属与截断语义**：  
    * 明确 `coverMaxChars` 属于**宿主策略（Host Policy）并冻结写入 `Source.recipe.coverMaxChars`**（与 `readMaxChars` 同级，见设计 §3.1），而不是自由请求参数（模型不可传任意 `coverMax` 绕过上限）。  
    * **取消部分 `cover` 截断时的 `isError: true`**：当 `span > coverMaxChars` 时，返回前 `coverMaxChars` 正文 \+ `[cover incomplete: N of M chars; next: ...]`，设置 `isError: false`，并在 `details` 中记录 `{ incomplete: true, covered: N, span: M, next: {...} }`。仅在参数互斥（如 `cover` 与 `length`/`page`/`line` 同传）或越界时抛出编码错误（`isError: true`）。  
* **阻断级别**：**设计阻断（Design-Blocking）** —— 必须在正式编码前锁定 `recipe.coverMaxChars` 字段与 `isError` 截断契约。

## **Q2. 触发层 `2/9` 缺口**

* **结论**：**有条件接受（Conditionally Accept —— 接受作为"被动工具路线的已知设计边界"并文档化，拒绝改为宿主无条件强制预取，同时提供结构路标与可证伪实验指标）**  
* **依据**：  
  * **证据支持的结论**：  
    * 在 `37K`（`t6l`）上，`C5` 的 `9` 次运行中有 `7` 次调用 `cover` 并全部答对，但仍有 `2/9` 完全未调用 `cover`（`render5-runs.json` 显示：1 条 `calls=0` 直接作答 `record_changelog=true`，1 条仅执行 `scan "changelog"` 后答 `true`）；`D5` 有 `4/9` 未调用 `cover`（3 条只读 `max`，1 条 `scan + max + 头部读取`），合并正确率 `5/9`（Wilson 95% `[0.27, 0.81]`，与 `C5` 的 `[0.45, 0.94]` 重叠）；无提示 `A` 在 `37K` 上为 `0/3` 覆盖（设计 §12.9 表；`out/render5-summary.json`）。  
    * 在 `15K`（`t6`）上，无提示 `A` 在 §12.8 合并 `1/9` 正确、`7/9` 零调用答错，在 §12.9 为 `1/3` 正确、`2/3` 零调用答错（设计 §12.8、§12.9）。  
  * **独立设计判断**：  
    * **为什么会出现 `2/9` 不触发？** 因为 `T6` 的可见头写了肯定句 `"a passing full test suite is sufficient; record the changelog entry immediately after it passes"`，且问题没有包含任何隐藏区关键词。在不允许压缩器做 LLM 语义判断的前提下，仅靠提示词提醒模型"先看 U 行是否有 hidden 跨度"，无法 100% 克服模型对可见肯定句的"过早满足（Premature Satisficing）"。  
    * **为什么拒绝"宿主层无条件强制覆盖/自动预取"？** 若宿主在生成视图时自动把 `cover` 附在视图后，视图就从 `6.2K` 膨胀到 `43.8K`，彻底摧毁压缩的意义；若宿主在模型每次作答前强制要求先读完所有 `hidden` 跨度，则当用户只问一个与 `#1` 无关的简单问题（如 `T1` 问最后一次测试通过数 `1139`）时，也会强制拉回 `37K` 历史文本，造成严重的成本浪费与未经请求的敏感历史暴露（违反设计 §1.1 与 §8）。  
    * **结构优于提示词的改进空间**：虽然不能做语义打分，但压缩器可以在渲染 `U` 行的 `hidden` 标记时，**零成本提取隐藏区间内的确定性结构标题（如行首 `###` 或 `Release-note correction:` 这类带冒号的大写节头名）**，或者将 `U` 行标记中的 `hidden` 警示前置到引用文本正上方与正下方（即在头摘录与尾摘录之间插入一行显式的结构断开行：`... [HIDDEN 37,414 CHARS (lines 10-325) OMITTED HERE — DO NOT ASSUME ABOVE EXCERPT IS COMPLETE; call cover/read] ...`，而不是只写在顶部行头方括号里！）。目前 `render.mjs` 第 213 行在打印 `U #1 [...]` 后，把头 9 行与尾 9 行**直接用 `\n` 连在一起打印**（没有像 `makeCharUserItem` 第 273 行那样在头尾摘录中间插入一行 `[hidden lines ...]` 分隔行！），导致头尾两段文本在视觉上无缝拼接，极大加剧了模型"以为中间没缺关键转折"的错觉！  
* **要求的修改**：  
  * **删除 `D5` 的 `STRUCTURE` 提示行**：在设计 §10.5 与 §12.9 中正式废除 `D5` 的额外结构解释行（实测 `5/9` vs `C5` `7/9`，无增益且增加系统提示词长度）。  
  * **修复 `render.mjs` 中 `renderQuotedLines` 的头尾摘录视觉拼接问题（结构级修改）**：当 `U` 或 `A` 行存在中间隐藏行（即 head 行与 tail 行不连续）时，必须在 head 摘录与 tail 摘录**之间**显式插入一行结构分隔符（例如 `[... hidden lines 10-325 (37414 chars); read/cover #1 @803 ...]`，计入预算 `B`），严禁把第 9 行和第 326 行直接相邻拼接成看似连续的段落。  
  * **将剩余触发缺口正式列为"设计已知限制（Known Design Limitation）"而非发布阻断项**：在产品 README 与设计 §1.2、§11.5 中写明："本插件提供 100% 可验证的目录与可执行地址，并通过系统提示词引导读取，但不做宿主强制预取，不承诺 100% 消除模型在局部摘录上的零调用作答"。  
  * **若继续探索提示词或中间分隔符路线，下一次可证伪预注册实验规范**：  
    * **预注册问题**：在 `t6l`（37K）与 `t6`（15K）上，在 head 与 tail 摘录之间插入显式中间结构断开行（含或不含确定性行首小标题名），是否比当前 `render-5`（头尾无缝拼接）降低未触发率？  
    * **主指标（Primary Endpoint）**：联合以 **`targetCoveredByRead`（提升）** 与 **`untriggeredRate = 1 - (usedMax ∪ usedCover)`（下降）** 为主指标，`groundedCorrect` 为共同主终点；单格样本量至少扩至 `n >= 15`（或跨 2 个模型 × 10 次）。  
* **阻断级别**：**非阻断（Non-Blocking，前提是如实文档化边界并刪除无效的 D5 行；中间分隔符建议在实现 P2 阶段纳入）**。

## **Q3. `cover` 成本与默认政策**

* **结论**：**有条件接受（Conditionally Accept —— 必须写入深读成本倒挂契约、收紧默认出现条件、明确 `coverMax` 所有权并设立单回合字符预算上限）**  
* **依据**：  
  * **证据支持的结论**：  
    * 单次字符倒挂事实：`37K`（`t6l`）上一次 `cover` 工具结果 `37,615 chars`（正文 `37,414 chars ≈ 11,916 tok`）+ 视图 `6,177 chars` \= **`43,792 chars`（约 `43.8K`）**，超过原始未压缩字段 `39,324 chars`；`15K`（`t6`）上一次 `cover` 工具结果 `15,474 chars` \+ 视图 `6,176 chars` \= **`21,650 chars`（约 `21.7K`）**，超过原始字段 `17,184 chars`（设计 §12.9 成本账；`out/probe-render5.json`）。  
    * 路由累计 prompt 事实：`37K` 上到达目标的路由中，单次 `cover` 累计 `promptTokens` 为 **`14,208`**，而连续两个 `next` 窗口为 `21,614`，三个 `next` 窗口为 **`28,167–28,171`**；`15K` 上单次 `cover` 累计 `promptTokens` 为 `9,342`，而两次 `max` 为 `15,090`（设计 §12.9 成本账表）。  
    * 宿主预算事实：`host-pi.mjs` 第 279–287 行（`out/host-checks.json` 第 77 行）证明 Pi 宿主没有内建 per-turn 工具调用预算，必须由扩展自行计数并抛出 `budget_exhausted`。  
  * **独立设计判断**：  
    * **压缩省 token 的充要条件必须写进产品契约**：压缩绝不保证在"单轮立即全量回读深跨度原文"时节省字符；它的经济收益完全来自 **(a) 大多数回合不需要回读那 359 条 `IndexOnly` 记录或长消息隐藏段**、**(b) 压缩视图在后续 N 轮对话中跨请求复用摊销**、以及 **(c) 当必须深读多窗口跨度时，一次 `cover` 比 3 次 `next` 翻页节省约 50% 的上下文重复发送 token（`14.2K vs 28.2K`）**。  
    * **`cover` 绝不应成为 `read` 的默认行为（即 `cover` 缺省必须为 `false`）**，也不应对所有 `span > 12,000` 默认内联打印（见 Q4）。  
    * **除了限制调用次数（`maxCallsPerTurn = 3`），扩展还必须限制单回合累计读取字符数（`turnReadBudgetChars`）**：否则模型若在同一回合内对 3 条不同的长记录各发一次 `48,000 chars` 的 `cover`，单回合将向模型上下文注入 `144,000 chars`（约 `46K tokens`），直接导致上下文再次溢出并触发连环压缩（compaction thrashing）。  
* **要求的修改**：  
  * **在设计 §1.3 与 §5 中写入《深读成本条款》**："本插件不承诺在立即深读场景下比未压缩原文节省单次字符；压缩收益仅在未展示记录不被立即全量读取、或视图跨多轮请求复用时成立；在必须读取跨多窗口隐藏段时，`cover` 的设计目标是降低多轮翻页的累计重发 prompt token，而非降低单次工具返回字符数。"  
  * **明确 `coverMax` 与回合预算的所有权及默认数值**：  
    * **所有权**：由\*\*宿主扩展配置（Host Extension Policy）\*\*拥有，并在压缩时写入 `Source.recipe.coverMaxChars`，同时约束 Reader 执行器；TypeBox schema 中 `read.cover` 仅声明为 `Type.Optional(Type.Boolean())`（默认 `false`），不允许模型通过参数上调 `coverMax`。  
    * **推荐产品默认值**：`readMaxChars = 12,000`（单窗口），`coverMaxChars = 36,000`（相当于 3 个标准窗口，约 `11,500 tokens`，若保持与原型一致则取 `48,000` 即 4 个窗口，但必须同时设单回合总读取字符上限 **`turnReadBudgetChars = 48,000`** 与单回合调用次数上限 **`maxCallsPerTurn = 3`**）。当单回合累计读取字符即将超过 `turnReadBudgetChars` 时，拒绝后续大读取并返回 `budget_exhausted`（附带本回合已用字符数与剩余额度）。  
  * **修改默认打印条件**：见 Q4 裁定（时间线仅对 `span > 24,000` 即 `windows >= 3` 内联打印 `cover`；对 `12,000 < span <= 24,000` 仅在 `max` 读取后的 `next` 尾行中提供剩余跨度读取）。  
* **阻断级别**：**设计阻断（Design-Blocking）** —— 必须在设计文档 §5/§7.4 中锁定 `coverMaxChars`、`turnReadBudgetChars` 及成本声明。

## **Q4. `15K` 时 `cover` 多余与打印门设计**

* **结论**：**拒绝当前"`span > readMax (12,000)` 即在时间线内联打印 `cover`"的宽门规则；要求改为"`span > 2 * readMax (24,000)` 内联打印 \+ `max` 结果尾部 `next` 续读"的双层打印门（无需为 15K 重跑即可先做契约收紧，阈值微调可留作探索预注册）**  
* **依据**：  
  * **证据支持的结论**：  
    * 在 `15K` 夹具（`t6`，隐藏跨度 `15,274 chars`，`windows=2`，目标偏移 `9,720` 位于第一个 `12,000` 窗口内）上，`render-3` 的 `C` 合并已达 `9/9` 正确（`P1 3/3 + R1 6/6`，全部复制 `max: offset=889 length=12000` 一次命中，设计 §12.8 合并表）；在 `render-5` 上，`C` 同样 `9/9` 正确（其中 `7` 次用 `max`、`2` 次自发用 `cover`），而加上覆盖规则的 `C5` 则 `9/9` 全部调用了 `cover`，导致平均工具字符从 `C` 的 `13,904 chars` 增加到 `C5` 的 `15,538 chars`（**`+11.7%`，约 `+12%`**），且没有任何正确率提升（同为 `9/9` 天花板，见设计 §12.9 `15K 与近距控制` 表、`out/render5-summary.json` 第 2502–2707 行）。  
    * 同时，因为 `render-5` 在 `t6` 的 `U #1` 行内联打印了 `cover: {...}`，挤掉了 1 行用户原文（`1-10 → 1-9`），使隐藏跨度平白增加了 `86 chars`（`15,188 → 15,274`，见 `out/probe-render5.json`）。  
    * 成本指标双面性：在 `15K` 上，虽然 `C5` 的 `toolCharsMean` 更高（`15,538 vs 13,904`），但 `C5` 的 `promptTokensMean` 反而略低（`9,706 vs 10,083`），原因是 `C` 中有 2 条运行发起了第 2 次工具调用（`calls: [1,1,1,2,1,1,1,1,2]`），多一次上下文重发消耗了约 `5,000` 额外 prompt tokens（设计 §12.9 发现 5、6）。  
  * **独立设计判断**：  
    * **为什么 `span > 12,000` 就打印 `cover` 是过宽的？** 当跨度为 `15,274 chars` 时，第一个 `max` 窗口（`12,000 chars`）已经覆盖了 **78.6%** 的隐藏内容，剩余未读尾部仅有 `3,274 chars`（不到 3 页）。此时如果直接在时间线并列打印 `max` 和 `cover` 并配合 `C5` 规则（"只要超过一个窗口就用 `cover`"），模型就会无脑放弃 `max` 而对所有 `>12K` 的跨度一律拉取全文，使 `max` 在 `>12K` 时沦为摆设（`C5` 在 `t6` 和 `t6l` 上的 `usedMax` 均为 `0`！）。  
    * **什么样的打印门最合理？**  
      * **门控规则 A（时间线内联打印门）**：仅当 **`span > 2 * readMaxChars`（即 `span > 24,000 chars`，`windows >= 3`）且估算 `cover` 成本 `<= coverMaxChars`** 时，才在时间线 `U` 行内联打印 `cover` 调用并激活 `C5` 规则。  
      * **门控规则 B（两窗口跨度的尾部精确续读）**：对于 `12,000 < span <= 24,000`（即 `windows == 2`）的跨度，时间线**只打印 `max`（12,000 chars）**。当模型调用 `max` 后，由于剩余未读部分必然 `<= 12,000 chars`（例如 `t6` 剩余 `3,188 chars`），`read` 返回结果末尾的 `[next: read #1 field="content" offset=12889 length=3189]` 本身就已经是一次性读完剩余全部内容的完整调用！這樣：如果目标在前 12K（占 50%–100% 概率），1 次 `max`（12K）即刻命中并结束；如果目标在后半段（12K–24K），模型只需按结果尾部的 `next` 再读一次剩余的几千字符。  
      * **成本指标规范**：报告成本时，必须将 **`promptTokens`（累计输入 token，决定真实 API 账单与延迟）** 设为主成本指标，将 **`toolChars`（单轮新增上下文占用）** 设为次要容量指标，严禁单凭其中一个宣称"更省"。  
* **要求的修改**：  
  * **修改设计 §6.3、§7.1、§10.5 与 §12.9 的默认打印门条款**：将时间线内联打印 `cover` 的阈值从 `span > readMaxChars (12,000)` 上调为 **`span > 2 * readMaxChars (24,000)`（即 `windows >= 3`）**；`12,000 < span <= 24,000` 保持 `render-3` 形态（只打印 `max`，不仅省去 15K 的多余 `cover`，还恢复被挤掉的第 10 行原文 `86 chars`）。  
  * **同步修正 `C5` 提示词触发条件**：将 `C5` 规则中的 `"longer than one read window"` 改为 `"when a U line prints a cover call (spans of 3+ windows)"`，使模型在没有打印 `cover` 的 2 窗口跨度上自然使用 `max`。  
  * **是否需要立即重跑？** **不需要在本次设计签字前重跑**——因为当 `t6`（15K）不打印 `cover` 时，其视图字节与 `render-3` 的 `t6`（`vfdaf9adb`，`6,177 chars`）完全一致，而 `render-3` 在 `t6` 上的表现已经由 §12.8（`C` `9/9`）和 §12.9 充分验证！但若要测试目标落在 `15K` 跨度的第 2 窗口（如 `offset=14,000`）时模型是否会在 `max` 后跟进 1 次 `next`，可在后续探索阶段新建预注册实验（见 §3）。  
* **阻断级别**：**设计阻断（Design-Blocking）** —— 必须在设计文档中修正默认打印门条款，不得将"15K 仍打印并触发 cover"保留为产品默认。
