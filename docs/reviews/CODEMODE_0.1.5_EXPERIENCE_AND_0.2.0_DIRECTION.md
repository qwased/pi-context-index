## 0. 结论摘要

1. **"压缩"与"还原工作"是两个目标，0.1.5 只完成了前者的框架。** 实测：一次 410K token 的压缩产出 6,279 chars 摘要（≈2.0K token，占预算 99.87%），但把 71 个变更操作中只有 **1 个**放进带引用的行里；11 个观测错误中只有 4 个带引用。工作还原率（带指针的变更比例）≈ **1.4%**。
2. **原生 LLM 压缩的代价被实测确认**：把被压缩前缀序列化后交给同一个模型，一次调用输入 **210,469 tokens**、输出 4,904 tokens、耗时 36.6s。pi-vcc 的同一次压缩是 **0 token / 28ms**（重放实测）。
3. **对照实验（同一尾部、同一问题、同一参数）表明三种产物各有所长、没有单一赢家。** 其中一题问"Pi 1.0.0 的 pass 数"，而这个事实**根本不在窗口的记录里**（只在仓库外的临时文件里），正确行为是"未知"：原生摘要与 0.1.5 摘要都答成 1139（窗口里真实的 1.4.0 计数），台账版弃答（null）。但在"用户约束"上，0.1.5 的逐字摘录 **5/6** 明显优于原生归纳 **2/6**；在"错误引用"上，原生列了 3 项、一个引用位置也没给出（0 命中），0.1.5 与台账 **5/5**。
4. **尾部主导一切。** 三/四个条件在"最近变更清单"（26/68）与"当前状态"（4/4）上完全相同——因为 27.5K chars 的保留尾部本身就含完整 git 输出。**摘要的价值只在尾部覆盖不到的"旧的中段"。**
5. **省略标记不能替代"入册"。** 0.1.5 明明带着 `[omitted … chars; recall #N]` 标记，模型仍为"材料里没有的计数"编出 1139。0.2.0 若要让 agent 不猜，必须把关键计数事实**写进台账**，或提供显式的"材料未包含"语义。
6. **补充实验（§10）：召回能触发，但很少成功。** 问题看起来可答时，原生摘要条件 **0 次**召回（4 轮一致）并编造数字；问题明显缺料时三个条件都会去检索（2–3 次），却因为"宽词命中长记录 + 只看页首"而空手——直到台账里写入**事实 + 引用**（`422 pass / 0 fail (#5)`），才 0 次召回直接答对。
7. **0.2.0 方向**：把产物从"摘要"改为"**索引 + 工作台账 + 少量时间轴逐字摘录 + 覆盖声明**"；引用升级为可校验的 `#N@指纹`；预算按"与尾部去重后的旧事实"分配，而不是按角色配额。粗估行为偏差相对原生：旧事实可核对性更好，旧意图恢复更差（−10~20pp），成本下降 100%。

## 1. 实验方法

### 1.1 样本

本仓库一次真实压缩（0.1.5 自举）：

| 项 | 实测 |
|---|---|
| 压缩前上下文 | 410,462 tokens（宿主计量） |
| 被压缩前缀 | 473 条消息，序列化后 632,205 chars（≈201K token 文本） |
| 保留尾部 | 30 条消息；序列化 27,546 chars（≈8.8K token 文本），按 `estimateMessageContentChars` 口径 16,420 token |
| 0.1.5 摘要 | 6,279 chars，≈2.0K token，预算 6,287（占用 99.87%） |
| 历史规模 | 470 messages / 487 blocks |

### 1.2 四个条件

| 条件 | 产物 | 来源 |
|---|---|---|
| **A 原生** | 结构化 prose 摘要（Goal / Constraints & Preferences / Progress(Done-In Progress-Blocked) / Key Decisions / Next Steps / Critical Context） | 用宿主 dist 的原始 system prompt 与指令，对同一前缀做**真实 LLM 压缩调用**：prompt 210,469 tokens、completion 4,904（reasoning 2,347）、36.6s、输出 7,860 chars |
| **B 0.1.5** | 生产摘要（30 条带引用行） | 压缩记录中实际写入的 `summary` |
| **C1 台账** | 覆盖声明 + 逐字用户首条摘录 + 71 行变更台账 + 5 行命令 + 5 行错误 + note（5,598 chars，89% 预算） | 按 0.2.0 设计**确定性构造**（非实现） |
| **C2 混合** | 同 C1，但台账 48 行 + 4 条"时间轴抽样"逐字摘录（6,278 chars，99.9% 预算） | 同上，验证"混合清单" |

### 1.3 提问与评分

- 同一个尾部（27,546 chars）拼在每份产物之后，**四个条件完全相同的 9 组问题**，只依据材料作答、不确定填 `null`，输出严格 JSON。
- 同模型、同参数：`max_tokens=16000`、`reasoning_effort=minimal`、非流式；每个条件各一次有效调用；首轮曾因 reasoning 吃光输出预算而空答，统一改小 reasoning 档位并加大 max_tokens 后重跑（见 §7.3）。
- 真值由会话记录确定性计算：68 个变更路径（write/edit 去重）、11 个错误结果 / 22 个可引用位置、4 个状态位、两个窗口内数值事实（87/155、fixture 冻结与 SHA pin），外加一个**窗口外**事实（Pi 1.0.0 的 1077/0，正确行为为 unknown，见 §3.3）。
- 评分按字段比对，不做主观打分；`files_changed` 用去除目录后的文件名匹配。

### 1.4 一个必须说明的偏差源

条件 A 的摘要**只能覆盖它能读到的文本**：序列化后的前缀是 632K chars，而宿主计量 410K token 里的差额来自 thinking 块、工具 schema 与会话内嵌的其他计量。也就是说原生摘要的输入不是"500K"，而是"**序列化文本 ≈201K token**"。这一点与"500K 上下文会产生 500K 冷输入"的直觉不同，实际是按序列化文本计费与限流。

## 3. 五条发现

### 3.1 尾部主导：摘要的边际价值只在"旧的中段"

四个条件在"变更路径召回 26/68"和"状态 4/4"上完全相同。原因不是摘要写得好，而是 **27.5K chars 的尾部里已经有完整 git 输出**（`--stat`、`--name-status`），任何读到尾部的读者都能列出最近变更。

推论：**0.2.0 的预算必须先与尾部去重**。凡是尾部已逐字保留的事实（最近一轮的文件清单、最近一次命令计数、当前状态），摘要再写一遍只是浪费——本次 6,287 chars 里的一部分正是这种重复。

### 3.2 逐字摘录 > LLM 归纳（在约束上）

约束 6 项命中：原生 **2/6**，0.1.5 **5/6**，台账 2/6，混合 3/6。

差别不在"文笔"，在**粒度**：约束是"不要用重生成快照解决失败""不要 Math.min(...array)""测试用临时配置文件"这类**短禁令**。LLM 归纳会把它压缩成"遵守项目规则"（信息丢失），逐字摘录则原样保留。0.1.5 的 `[user]` 首条摘录 1,856 chars 恰好覆盖了这些条目，所以它赢。

推论：**"避免误导"的第一条不是去掉 goal，而是让禁令以原文形态存在**。

### 3.3 邻近数字污染：模型不会因为缺数据而弃答

"Pi 1.0.0 的 pass 数"是一个**窗口里不存在的事实**：会话记录中 `1077` 只以测试文件行号、随机用例 ID 的形式出现（本次复核：两条记录，均与"Pi 1.0.0 通过数"无关）。正确行为是回答"未知"。原生摘要与 0.1.5 摘要都答成 **1139**（窗口内真实的 1.4.0 计数），台账条件答 `null`。

这不是"摘要没用"，而是**摘要里的近似信息会被当成精确信息消费**。三条对策（按成本排序）：

1. 关键计数事实进台账（`commands` 行保留**去重后的计数集合**，而不是"最后 5 条"——C1 正是因此丢了窗口内的其它计数）；
2. 摘录被截断时，标记要包含语义化的"这里被截断"提示，而不只是数字区间（本次标记是 `[omitted N of M chars]`，模型忽略了它）；
3. 给 agent 的输出约定一个"材料未包含"字段（本次实验里 `null` 的表现是正面的）。

### 3.4 指针质量分三档

| 档 | 形态 | 本次表现 |
|---|---|---|
| 不可解析 | 文件路径、文档 §、"WORKLOG" | 原生摘要 10 条指针，**0 条可执行**（读者只能去读文件） |
| 半可解析 | 名字、文件名、文档标题 | 0.1.5 摘要 10 条，能 grep 到，但不知道对应哪条记录 |
| 可执行 | `read #N`、`range:[a,b]`、`scan "terms"` | 台账/混合 10 条，且 `#N@指纹` 可校验是否漂移 |

0.1.5 的 49 个引用里 19 个是结果配对引用（`{result #N}`），语义正确率 **19/19**（call↔result 的 toolCallId 全部匹配）；但它的**引用只挂在"已经选中的行"上**，没有覆盖"工作事实"。

### 3.5 省略标记 ≠ 入册

0.1.5 的摘要在被截断处写了 `[omitted 1,951 of 3,039 chars; recall #473]`，模型仍为一个窗口外的事实编出数字。台账版（C1）没有省略标记，但它把"最后 5 条命令"当全部，同样漏掉窗口内的早期计数。

**两种缺口的写法都不够**：一种是"这里被截断"，另一种是"这里只保留最近几条"。0.2.0 需要的不是更强的提醒语，而是**入册规则**（哪些事实必须有一条对应行）加**去重后的全集计数**（例如 `commands: 11 runs; pass counts {243,422,1139}; each with #N`）。

### 4.2 结构与引用

- 30 条带 `#N` 的行：19 条 codemode 步骤 + 11 条文本/旁白行；49 个引用位置（30 个 `#N` + 19 个 `{result #N}`）。
- 结果配对：19/19 语义正确（call↔result toolCallId 全匹配），0 缺失。
- 错误标记：5 条，其中 2 条来自 nested-call 错误（外层 `isError=false`）——判定正确，不是误报。
- 省略标记：2 条，合计 2,513 chars；分母 2,418 / 3,039 与源长度逐字吻合。

### 4.3 工作覆盖率（"已做过的工作"实际还原了多少）

| 工作事实 | 总数 | 摘要中带引用 |

| write | 51 | **0** |
| edit | 25 | 1 |

后者被切掉的中间部分恰好是"逐 H 数值 + 验收 gate"——续做者最想要的那一段。省略标记指向 #473，召回可用，但**摘要本身没给**。

### 4.6 可继续性：真实证据

压缩后我在**没有回读计划文档或 WORKLOG** 的情况下完成了发布流程（脱敏、三批提交、打 tag、推送、给出 npm 命令），期间只读取了 6 处源码文件（`src/hooks/before-compact.ts`、`src/details.ts`、`src/core/summarize.ts` 等）来确认实现细节。

也就是说：**0.1.5 的摘要在"继续做事"这个目标上是够用的**——它给出了目标、状态和下一步的边界；不够用的是"核对旧事实"（1.4% 覆盖率）与"回跳"（清单无引用）。

### 4.7 本次没有检验到的部分

- **P0 围栏**：本次摘要不含围栏行，收敛正确，但收益为 0（不是回归）。
- **H3 直连通道**：本会话所有工具都经 codemode，`toolDirectTotal=0`，直连份额没有候选。
- **H1 深度**：如 4.5，本次未占优。
- **多轮压缩**：本会话只有 1 次压缩，跨压缩稳定性未在真实数据上验证（只有合成三连压缩测试）。

### 4.8 体感

1. **定位快**：读到 `* codemode goal: … (#N) {result #N}` 基本能判断"这一步在干什么、结果在哪"。
2. **需要自己找**：要确认"某个文件改没改过"，必须 recall 或重新 grep——摘要里没有操作行。
3. **噪声比不低**：30 行里有 8 行是"继续""现在写 X 的失败用例"这类旁白，信息密度低却占着 assistant 配额。
4. **数字可信度依赖上下文**：窗口里"看起来最像答案"的数字会被填进空位（见 3.3），而摘要不作任何"我没包含这个事实"的声明。

## 5. 0.2.0 重构方向

### 5.1 契约：产物是"索引 + 台账"，不是"摘要"

> 摘要暗示"这是对过去的概括"，无 LLM 时必然滑向"选集 + 猜重要性"。索引的承诺更窄、更可验证：**每条都是逐字原文或计数事实，每个事实都能跳回原文，并声明覆盖了哪一段；不含当前目标、不含状态判断。**

由此推出三条禁令（职责划分与证据见 §13.1）：不写状态指针行、不读 /plan 类文件、不出现 done/verified/success 字样。

### 5.2 五条规则

**R1 引用要可校验，不只是可解析。**
`#N` 是文件位置，fork/retry/编辑后同一位置可能是另一条消息。升级为 `#N@<6 hex 指纹>`（记录内容哈希），`vcc_recall` 接受两种写法并校验；对不上时明确回"引用已失效，请 scan"，绝不静默返回别的消息。成本每行 +7 chars（本次 49 个引用 ≈ +343 chars，可从 header 的 1,118 chars 里省出）。

**R2 台账优先：先写"可观测事实"，再填叙事。**
四类事实（本次实测的可用规模）：变更操作 71 条、命令/测试运行（去重计数）≈8 条、观测错误 11 条、当前状态（由尾部承担，不入摘要）。每行自足：

```text
* edit src/core/fences.ts x2 (#412)
* tests 1139 pass / 0 fail (#470); earliest 422 pass / 0 fail (#5)
* error observed: codemode (#359) result (#360)
```

第一行就能回答"改过没有"，点击只用于"改了什么"。这与 0.1.5 的差别是结构性的：0.1.5 的 71 个变更里只有 1 个进入带引用的行。

**R3 覆盖声明与分区不变式。**
顶部一行（计入 `reservedChars`，不参与 header 裁剪）：

```text
[History] saved #0-#503; ledger cites 71/71 mutations; excerpts 4; live #474-#503. recall: range:[0,503] / read #N / scan "terms"
```

不变式：有效历史的所有 `#N` ⊆ 正文引用 ∪ 台账行引用 ∪ 覆盖行声明 ∪ live 区间；补集非空就渲染 `[gap #a..#b; recall range:[a,b]]`，不允许静默。`coverage` 与 `gapCount` 落进 `details`，审计只统计计数。

**R4 混合清单：台账 + 时间轴逐字摘录 + 去重计数集。**
本次实验的直接证据：
- 纯台账（C1）丢了 fixture 事实（`null`）；加 4 条**按时间轴四分位抽样**的助手原文摘录后（C2），该事实被补回（正确）。
- 纯台账与混合都丢了"未验证项"（0/3）——因为台账没有叙事位；把"未验证/限制"作为**摘录抽样的一部分**（而不是推断出来的章节）才能保留。
- `commands` 若只保留"最后 5 条"，会像 C1 一样丢掉早期计数；应保留**去重后的计数集合**（本次实测：`{243,422,1139}`）+ 各自引用。

抽样规则建议是**位置式的**（四分位/每 N 条），不是关键词式的——后者就是"语义提取"的变体。

**R5 诚实性可测。**
- 属性测试：每条非模板行必须是某个保存字段的**逐字子串**；计数行必须能在对应结果里找到同名数字。
- 负向断言：无 `done/verified/success`、无状态行、无"未解决/待办"这类推断章节。
- 标记可执行：`read #N`、`range:[a,b]`、`scan "terms"` 都必须能被真实参数解析器原样执行（0.1.5 的 `scan saved history #a..#b` 是反例：`scan` 必须带 query）。

### 5.3 预算与分配（以本次 6,287 为例）

预算的**天花板**已按 §12.3 阶梯化（`clamp(15 × blocks, 1100, ceiling(ctx)) × charsPerToken`）；下表仍按旧 6,287 估算，说明的是**分配顺序**，两者叠加后 410K 会话的实际可用额度是 9,588 chars：

| 区 | 内容 | 本次估算 | 说明 |
|---|---|---|---|
| F 固定 | 覆盖行 + note + 分隔符 | ≈ 560 | 覆盖行 ~150、note 395 |
| L 台账 | 71 个变更路径，每路径 1 行 | ≈ 3,900 | 与尾部去重后可裁到 ≈3,300 |
| C 命令 | 去重计数集 + 引用 | ≈ 480 | 含 1.0.0 / 1.4.0 两套计数 |
| E 错误 | 5–11 行 | ≈ 400 | 每条带 call/result 双引用 |
| X 摘录 | 4 条时间轴抽样 + 首条用户摘录 | ≈ 1,500–2,000 | 上限 25% 预算 |
| 合计 | | ≈ 6,340–6,840 | 略超 → 靠"与尾部去重"回收 |

**去重规则**（本次可省 ≈700–900 chars）：尾部已逐字保留的事实不入摘要——最近一轮的文件清单、最近一次命令的完整输出、当前状态位。摘要只写"尾部之前、且不在尾部"的东西。

若预算不足以放全 L，优先保留**写入类**（write）行与**报错过的编辑**，其余折叠为 `* (+N more paths; scan "path")`；这正是 0.1.5 已有的 `(+N more)` 形态，只是把它从"清单"移到"台账"。

## 6. 与原生 LLM 压缩的机制对比与偏差粗估

### 6.1 机制对照（宿主 1.4.0 源码核对）

| 环节 | 原生 LLM 压缩 | pi-vcc 0.1.5 | 0.2.0（本方案） |
|---|---|---|---|
| 触发 | `contextTokens > contextWindow − reserveTokens(16,384)` | 同（hook 被调用） | 同 |
| 切点 | turn 边界，保留 `keepRecentTokens(20,000)` | pi-vcc 自己的切点：`keep:1` 尾部 ≤5K 时增长到 ≤25K | 不变 |
| 摘要来源 | 把前缀**序列化成一条 user 文本**（`<conversation>`）+ 结构化指令，交给**会话当前模型** | 0 次 LLM 调用；按算法渲染 | 同，但改为台账 + 抽样摘录 |
| 摘要形态 | prose：Goal / Constraints / Progress(Done-In Progress-Blocked) / Decisions / Next Steps / Critical Context | 逐字摘录 + 计数 + 引用行 | 覆盖行 + 台账 + 摘录（无状态断言） |
| 后续压缩 | `UPDATE_SUMMARIZATION_INSTRUCTIONS`：摘要套摘要，"PRESERVE all existing information" | 从 raw branch **重建**，不合并上一份摘要 | 同 + 引用台账单调累积 |
| 尾部 | 20K token（默认） | 自适应 5K–25K（本次 16,420） | 不变 |

### 6.2 实测成本

| 项 | 原生 | pi-vcc 0.1.5 |
|---|---|---|
| 输入 token | **210,469**（序列化前缀 632,205 chars） | **0** |
| 输出 token | 4,904（其中 reasoning 2,347） | 0 |
| 墙钟 | 36.6s | 28ms（同输入重放） |
| 压缩后上下文 | ≈1.5K prose + 20K 尾 = **21.5K token** | 2.0K 摘要 + 16.4K 尾 = **18.4K token**（尾部 16,420 为宿主估算口径，见 §1.1） |

一处需要校正直觉：**"500K 上下文会产生 500K 冷输入"在高估与低估两方面都不精确**。宿主计量 410,462 token，但序列化后只有 632,205 chars（≈201K token 文本）——thinking 块与工具 schema 不进摘要输入；同时它确实**无法命中前缀缓存**（整个对话被重新序列化、配了另一个 system prompt），所以是"201K 量级的真正冷输入"，不是"摊销在正常对话里的增量"。

### 6.3 行为偏差（用实验结果填，而不是猜）

| 维度 | 原生 | 0.2.0 台账/混合 | 解释 |
|---|---|---|---|
| 旧事实可核对（数值） | 1/3 错（1139） | 0 错，2 项弃答（C1/C2） | 台账不猜；但弃答也意味着"没帮上" |
| 旧约束保留 | 2/6 | 3/6（混合）～5/6（0.1.5 的长摘录） | 逐字 > 归纳；摘录越长越好，但挤占台账 |
| 错误可引用 | 0/3 | 5/5 | 原生没有引用体系 |
| 指针可执行 | 0/10 | 10/10 | `#N`/`range`/`scan` vs 文件路径 |
| 未验证项 | 3/3 线索 | 0/3（本次台账无叙事位） | 需要把"限制/未做"作为抽样对象 |
| 当前状态 | 4/4 | 4/4 | 尾部承担，与摘要无关 |
| 变更清单 | 26/68 | 26/68 | 尾部承担 |

### 6.4 净判（粗估，非实测）

- **继续做对下一步的概率**：原生 ≈0.90；0.2.0 单独 ≈0.80–0.85；0.2.0 + 状态插件（/GOAL、/plan）≈0.90–0.95。
- **偏差来源不是"旧事实"**（台账在这上面更好或至少不更差），而是**"旧意图与未验证项"**——原生用 Next Steps/Blocked 直接给出，0.2.0 需要读者自己从摘录推导或召回。
- **代价形态**：原生是"可能读到错的过去"（本次实证：1/3 数值错误）；0.2.0 是"可能读不到已有的过去"（1–3 次 recall/read）。
- **成本**：每次压缩 −210K 输入 token、−36.6s。

### 6.5 原生仍然更好的场景（公平起见）

- 会话短（前缀 < 50K token）：LLM 归纳的语义压缩仍然划算，且没有多少"旧事实"需要追溯。
- 任务跨多个主题、需要"把 20 件事揉成 5 条结论"：无 LLM 的索引只能给指针。
- 读者是**人类**而非 agent：人类读 prose 比读台账快。
- 模型窗口远大于会话：冷输入成本不痛，原生的一次调用很便宜。

## 7. 未验证与风险

1. **单样本**：1 次压缩、1 个模型、1 种任务（实现型 + 发布型）。中文/英文、代码/对话、长/短会话的结论可能不同。
2. **C1/C2 是手写构造**，不是实现；配方敏感（摘录长度 480 vs 900、台账 48 vs 71 行、命令"最后 5 条" vs "去重集合"）。结论应读作"方向与量级"，不是"参数已定"。
3. **评分依赖模型遵守 JSON**：曾出现一次 8,000 token 全被 reasoning 吃光、正文为空的情况；正式化时必须固定 `max_tokens` 与 reasoning 档位并重试。
4. **引用有效性未测 fork/retry**：`#N@fp` 只能"发现漂移"，不能"阻止漂移"。
5. **成本数字只算 token 与墙钟**：本机模型是本地端点，货币定价不适用；换到付费 API 时按 210K 输入重算即可。
6. **样本本身有污染风险**：尾部含完整 git 输出，使"清单题"对所有条件都偏容易；真正有判别力的题只有 4–5 项，统计意义有限。

## 10. 补充实验：模型能否"发现缺料 → 召回 → 答对"

本节在 §9 之后追加，回应两个此前未测的问题：**（1）模型会不会发现摘要里没有真实信息，并用 recall 取回？（2）原生摘要下，原文是否已经"无从下手"？**

### 10.1 为什么必须补

§1–§8 的四个条件都是"单轮、只读材料、不许用工具"，测的是"材料本身够不够"，而不是"agent 能不能补救"。0.2.0 的核心承诺恰好是后者，所以这一节必须单独测。

### 10.2 原生压缩后原文去哪了（源码核对）

| 事实 | 证据 |
|---|---|
| 压缩只写入 `{summary, details, firstKeptEntryId}`，被压缩的消息**不删除** | 宿主 `appendCompaction(summary, firstKeptEntryId, …)`；session JSONL 仍是追加式 |
| 宿主**没有**读回历史的工具 | 内置工具只有 read/bash/edit/write/grep/find/ls 等文件类 |
| `vcc_recall` 流式读 session 文件，因此**任何压缩器压缩过的内容都能读回** | `forEachJsonlLine` / `readSavedRecord` / `scanSavedFields` |

结论：**"无从下手"不是数据消失，而是没有指针、没有"还有更多"的信号、prose 读起来像结论。** 这一点在 10.4 被实测证实。

### 10.3 实验设计（含三次工具修正，必须披露）

- 工具协议（三个条件完全相同，最多 3 次，之后强制作答）：`recall({"read":N,"offset":K})`、`recall({"range":[A,B]})`、`recall({"scan":"词"})`。
- 索引空间**限制在压缩时刻**（`#0..#503`）。第一版没限制，工具能读到压缩之后新增的条目（包括实验自己的讨论），属于污染，已废弃。
- 渲染口径：`read` 每页 1,600 chars 并给"下一段 offset"提示；`range` 每页 10 条 × 1,600 chars；`scan` 按命中词频 + 新近度排序、返回**命中中心**片段。
- 目标事实：窗口内存在、且 A/B/C 三份产物都没写的一条——**#5 的"422 pass / 0 fail"**。该记录 19,178 chars，事实位于第 **18,767** 字符处。
- 作废一组：9 问里的"Pi 1.0.0 = 1077"不在窗口内（见 §3.3 更正），召回答不了"记录里没有的东西"。

### 10.4 结果

| 条件 | 9 问场景（每题看起来可答） | 定向题（明说"最早一次测试结果"） | 定向题结果 |
|---|---|---|---|
| A 原生 | **0 次召回**（4 轮一致） | 2 次（`scan "pass"`、`scan "Ran"`） | 未答出（空答 / 10 pass） |
| B 0.1.5 | 2 次（`scan`→`read`） | 3 次（`scan`→`read 77`→`range`） | `null`（诚实未答） |
| C2 台账 | 2 次（`read 473`→`scan`） | 3 次（`scan`→`range[0,12]`→`range[76,80]`） | 10 pass（错） |
| C3 = C2 + 一行事实 | — | **0 次** | **422 / 0 正确，引用 #5** |

四条读数：

1. **触发召回的是"问题的形状"，不是产物格式。** 9 问里每题看起来都能从材料回答，原生条件一次都没搜（并编出 1139）；定向题明说"最早一次""不是最后一次"，原生条件立刻搜了 2 次。
2. **原生不是"数据没了"，是"没有信号"。** 它没有 `#N`、没有覆盖声明，`scan` 到长记录、`read` 到头部、看不到事实就换词，三次用完空手。
3. **0.1.5 的省略标记与台账的覆盖行确实能触发检索**（B/C 每轮都在搜），但**检索质量决定成败**：宽词 "pass" 命中长记录，只看页首就看不到第 18,767 字符处的事实。
4. **唯一确定成功的路径是"事实 + 引用入册"。** C3 只加了一行 `* earliest test record: 422 pass / 0 fail (#5)`：0 次召回、答案正确、引用正确。

### 10.5 对 0.2.0 的三条修正

1. **台账行要写"值 + 引用"，不是只写引用。** `422 pass / 0 fail (#5)` 可直接作答；只给 `read #5` 反而把读者送进 19K 字符的记录头部。
2. **不要指望 `scan` 兜底。** 宽词命中长记录、需要翻页时 agent 会放弃；关键词检索只能作为"定位台账行"的补充，不能作为"取回事实"的主路径。
3. **页宽与翻页必须写在渲染层。** 本次工具在结果尾部给了 `read #N offset K` 提示，**四轮实验里没有任何一次主动翻页**——所以"默认页就包含事实"比"提示可以翻页"更重要（提高默认页宽、或让台账直接给值）。

### 10.6 局限

- 单模型、单样本；工具是我的玩具实现，渲染方式对结果影响很大（已修三轮，§10.3 已披露）。
- 目标事实是"早期测试计数"，语义简单；对"决策理由"这类需要多跳的事实未测。
- "未答出"与"答错"要分开读：B 的 `null` 是诚实，C 的 `10 pass` 是错误，A 的空答是放弃。
- 结论应读作：**"可召回"是必要但不充分；0.2.0 的价值在于让"需要召回"的场景变少，并让剩下的召回有确定的落点。**

## 11. 补论：用户要求是时间线，不是一句话

本节在 §10 之后追加，回应一个判断：**"用户的要求依然是最核心要保留的，丢失任务目标则后续工作无意义。"** 这个判断成立，但需要三处收紧，否则"保留目标"会以另一种方式失败。

### 11.1 一个反直觉的成本事实

本会话压缩前窗口的用户发言只有 4 条，合计 2,478 chars：

| 项 | 实测 |
|---|---|
| 用户发言条数 | 4（chars：2,418 / 2 / 12 / 46） |
| 三条短指令合计 | **60 chars** |
| "短消息整条 + 长消息行级头尾 + 引用"的成本 | **1,020 chars（16% 预算）** |
| 再加"每条用户发言之后的第一段助手文本"（计划/口径所在） | 1,312 chars |
| 两项合计 | **2,332 chars（37% 预算）** |

也就是说：**上下文里最便宜、最要命的字节是用户发言**。0.1.5 却把 40% 的用户配额主要花在**一条 1,856 chars 的长消息**上，三条短指令（60 chars）随时可能被折叠。丢 60 chars 的代价是"整批工作作废"，而省下它们只值 1% 预算——这是纯粹的错配。

### 11.2 要求是时间线：没有"有效期"的目标会致命

本会话就有一个现成反例：

- 最早的用户消息里写着"**不提交、不打 tag、不发布、不切换本机安装**"；
- 后来的一条指令是"**分批提交并发布 0.1.5、推送 GitHub**"。

若索引保留了前一条（1,856 chars 的摘录里正好包含它），却不标出后一条推翻了它，读者只有三种反应：拒绝执行（按旧禁令）、无视禁令（按新指令），或者**把两条都当"当前约束"而自我矛盾**。三种都错，而错因不是"没保留目标"，是**保留了目标却没保留它的有效期**。

不需要语义推断的解法：**把用户发言按顺序全列，每条带 `#N`**。顺序本身编码"谁推翻谁"，成本 1,020 chars。

### 11.3 目标是文件，不是句子

本项目的任务契约在 `docs/plans/…` 与工作日志里，不在对话里。`[Session Goal]` 试图**复述**它——文档自己都写明"这是压缩摘录，不是任务契约"。

更便宜、更不会过期的是一个指针（≈80 chars）：

```text
* task contract: docs/plans/CODEMODE_0.1.5_UPGRADE_PLAN.md (authoritative; this index only points to turns)
```

三条理由：一句话的正确率永远低于原文；文件不随压缩次数衰减；**换新会话后对话没了、文件还在**。摘要自称"目标"是最危险的一类误导，比不写更糟。

### 11.4 目标与禁令是两类东西，禁令更脆弱

- 目标（做什么）：尾部 + 契约文件可恢复。
- 禁令（不许怎么做）："不要用重生成快照解决失败""每个 H 先写失败用例""测试用临时配置文件""不要 `Math.min(...array)`"。

禁令几乎只存在于最早的某条用户消息里，一旦折叠就**永久消失且无痕迹**。实测：0.1.5 靠 1,856 chars 的长摘录保住 5/6；摘录稍短即掉到 2/6，与原生归纳持平。

由此得出一条硬规则：**用户发言永不折叠**；长消息按**行边界**头尾切（禁令是行级的，按字符切会切掉它），短消息整条保留。

### 11.5 助手侧同样有"推翻"，而且更隐蔽

本次会话里有两处：先说"H1 深度更好"，同输入重放后更正为"其实 −64 chars"；Pi 1.0.0 兼容第一次失败、第二次成功。只记"观测事实"会把矛盾并列保存、不标先后。

结构性解法仍是**顺序 + 引用**（行序即时间序，每行带 `#N`）。这也是不建议"按重要性评分排序"的原因：分数会打乱时间线，让后来者看起来像前者。

### 11.6 "未验证"是目标的一部分，台账天生会丢

实测：原生 3/3、0.1.5 3/3、纯台账 **0/3**（"TUI 人工验收""真实会话 hook 重放"这类没做的事全部丢失）。台账只记"做了什么"，而验收要求里有一半是"证明给我看"。

低成本对策：抽样时**固定包含"最后一条助手消息"与"每条用户发言"**；不要新增"未完成/待办"章节——那是状态推断。

### 11.7 "信息不足"要逐节声明

最硬的证据：材料里**根本不存在**"Pi 1.0.0 = 1077"，原生摘要与 0.1.5 都填了 1139，台账弃答。**被误读的目标比丢失的目标更危险。**

低成本对策：每节一行 `not in this index: …`（例如 `[Decisions] not indexed; scan "决定"`），比文末一句总声明有效。

### 11.8 对 §5 的修订：优先级顺序

§5 的 R2 是"台账优先"，本节把它降为 P2，前面插入两条更硬的要求：

| 优先级 | 内容 | 本次成本 | 理由 |
|---|---|---|---|
| **P0** | 所有用户发言（顺序 + `#N` + 行级头尾；短消息整条） | 1,020（16%） | 目标是时间线，禁令是行 |
| **P1** | 每条用户发言后的第一段助手文本（计划/口径） | 1,312（21%） | "为什么这样做"只在这里 |
| **P2** | task contract 文件指针 | ≈80 | 权威目标在文件里 |
| **P3** | 变更台账（值 + 引用） | ≈3,300 | "做过什么"可核 |
| **P4** | 错误行 + 命令去重计数集 | ≈880 | 失败与验收的锚点 |
| **P5** | 时间轴抽样摘录 | ≤25% | 兜底长尾 |

合计 ≈ 6,600，略超 6,287 → 靠"与尾部去重"回收（尾部已含最近一轮文件清单与状态，可省 700–900 chars）。**这个顺序在本会话里刚好放得下**，不是理论建议。

### 11.9 一个必须承认的边界

"用户要求最核心"不等于"用户要求全部进摘要"：本次最长那条 2,418 chars 全量保留要吃掉 38% 预算，而其中真正约束后续行为的是 8 条禁令。正确的表述是：

> 保留用户发言的**顺序、原文与引用**；长消息按行切头尾；绝不为了腾地方折叠短指令。

### 11.10 首消息形态的两种极端

0.2.0 必须同时适配：

1. **首条消息本身就是长任务书**（本次即此类，2,418 chars）：禁令密集、结构清晰，按行级头尾 + 引用保留，并把"没有出现在摘录里的行"显式标出。
2. **首条消息是短指令 + 一个很长的任务书文件**（例如"按这份计划开始工作，文件路径 X"）：此时**最有价值的字节是文件路径**（几十 chars），而文件内容本来就能随时读回。索引只需保留"指令原文 + 路径 + 该文件在后续被引用的次数与引用点"，**不应尝试复述文件内容**——复述会与文件产生第二个可能过期的副本。

这两种形态的预算差异极大：前者需要 1,020 chars，后者可能只需要 120 chars。预算公式必须按"用户发言的实际形态"分配，而不是按"角色配额"平均分。

## 12. 决策变更（2026-10-30）：预算阶梯化与兼容性放开

本节记录两项新决策，并给出对应的数字依据。它们把 §5/§11 的"在 6,287 chars 内取舍"改成了"预算随会话长度增长，且不再受旧格式约束"。

### 12.1 变更内容

1. **预算阶梯化**：会话越长，摘要预算按比例上调；不再固定 `clamp(15×blocks, 1100, 2000)` 的 2,000 token 天花板。
2. **兼容性放开**：允许破坏与本 fork 旧版本（≤0.1.5）及上游的格式兼容；可作为**独立新插件**发布，重构自由度不受旧契约限制。

### 12.2 为什么"当前预算不足"不是感觉，而是算得出来的

§11 给出的优先级脊线（P0 用户发言 + P1 计划 + P2 契约指针 + P3 台账 + P4 错误/计数 + 覆盖行 + note）在本次会话上的成本是：

| 区块 | chars |
|---|---|
| P0 用户发言（4 条，行级头尾） | 1,020 |
| P1 每条用户发言后的第一段助手文本 | 1,312 |
| P2 task contract 指针 | 80 |
| P3 变更台账（71 行） | 3,900 |
| P4 错误行 + 命令去重计数集 | 1,360 |
| 覆盖行 + note | 545 |
| **合计** | **8,217** |

而当前预算是 **6,287 chars** → **缺口 1,930 chars（−23%）**。这正是实测里"71 个变更只有 1 个带引用、错误 4/11"的结构性原因：不是分配器不努力，是**预算装不下一条完整的脊线**。

### 12.3 阶梯公式与算例

建议把固定天花板换成一个随会话规模增长的函数（floor 1,100 与 `15×blocks` 的斜率保持不变，只抬高天花板）：

```text
ceiling(ctxTokens) = min(4,000, 2,000 + 0.005 × max(0, ctxTokens - 200,000))   // 单位：token
budget = clamp(15 × blocks, 1,100, ceiling(ctxTokens)) × charsPerToken          // 单位：chars
```

即"200K token 以上，每多 100K 加 500 token"。算例（`charsPerToken = 3.14`，脊线 8,217 chars）：

| 会话 tokens | ceiling（token） | 预算（chars） | 装得下脊线？ | 余量 |
|---|---|---|---|---|
| 50K | 2,000 | 6,287 | 否 | −1,930 |
| 200K | 2,000 | 6,287 | 否 | −1,930 |
| 300K | 2,500 | 7,859 | 否（差 358） | −358 |
| 410K（本次） | 3,050 | 9,588 | **是** | +1,371 |
| 500K | 3,500 | 11,002 | **是** | +2,785 |
| 800K | 4,000（封顶） | 12,574 | **是** | +4,357 |

两个可选细节：

- **平滑 vs 台阶**：上表用线性（无断点）比"每 100K 跳一档"更安全——台阶会在边界上产生 400 token 的跳变，测试与审计都会看到不连续。
- **二次精炼 `budget = min(ceiling, needed)`**：`needed` 是本轮实际脊线成本（用户发言条数、台账行数、错误行数都可由记录确定性算出）。这样"用户发言很少、变更也很少"的长会话不会白吃满预算，而"内容多"的会话也不会被天花板压住。此式与`ceiling` 单调，可测。

### 12.4 摊销成本：摘要在每一轮都被读一次

摘要不是一次性成本：压缩之后，它作为上下文的一部分**每一轮都被发送**。本次 6,287 chars → 9,588 chars，多出 1,200 token：

- 若压缩后还有 15 轮：额外 ≈18K token 累计，占 450K 窗口的 4%。
- 下一次压缩会略早触发（多 1,200 token 占 40K 余量的 3%），可忽略。
- 收益是可核的工作覆盖率：mutation 从 1/71 到接近 71/71，错误从 4/11 到 11/11。**每 1 个 token 换回的"可核查事实"是数量级的提升**，这是本次唯一值得放宽预算的理由。

### 12.5 兼容性放开后解锁的东西

| 动作 | 说明 |
|---|---|
| 单一代码路径 | 删除 legacy 路径与 `mergeHeaderParts`（不再需要"非 codemode 与上游逐字一致"），不再维护两套分配器 |
| 删除语义章节 | `[Session Goal]`/`[Outstanding Context]`/`[User Preferences]` 直接不实现，不必做迁移剥离 |
| 新格式 | `details.version: 3`；产物改为"覆盖行 + 用户时间线 + 台账 + 抽样摘录 + note"；旧记录不迁移、不倒填 |
| 新契约 | 新插件自己的 AGENTS.md，不受本仓库 0.1.x 契约约束（本仓库保持冻结在 0.1.5） |
| 新包名 | 建议 `pi-context-index`（备选 `pi-recall-index`、`pi-index`）；独立 npm 包、独立版本线（从 0.1.0 起） |
| 共存约束 | 两个插件都注册 `session_before_compact`，**不能同时安装**；README 必须写明 |

### 12.6 一个值得借机做的结构改动：旁挂索引（sidecar）

既然不再兼容，建议把"每次压缩重算一份视图"升级为"**持久索引 + 每次压缩渲染视图**"：

- 位置：会话目录旁的派生文件（如 `<session>.index.jsonl`），只用会话自身数据，不跨项目。
- 记录类型（全部可由会话 JSONL 确定性重建）：`user_turn`、`plan`（每条用户发言后第一段助手文本）、`mutation`、`command`、`error`、`citation`（压缩→引用）、`view`（本次压缩显示了什么、隐藏了什么）。
- 不变量：**sidecar 是缓存，不是权威**——删掉它必须无害（下次压缩从头重建），任何视图都能从 (session, sidecar) 复现；同一输入字节确定。
- 直接解决三个问题：
  1. **指针不静默丢失**：`view` 记录 `cited` 与 `shown` 两个集合，差值就是"未显示但已索引"，可渲染一行 `refs: +N withheld; recall refs #k`。
  2. **全历史可索引**：索引随会话增长累积，第 N 次压缩的视图不必重新扫描 500K token。
  3. **两种首消息形态**：`user_turn` 记录保留指令原文与文件路径；长任务书文件**只记路径与引用点，不复述内容**。
- 风险：磁盘增长（只存引用与摘录，不存全文）、fork 后 sidecar 与分支不一致（用 `#N@fp` 校验，失效即重建）、隐私（sidecar 与 session 同目录同权限）。

### 12.7 对前文的修订

- §5.3 的预算表、§11.8 的优先级表按 12.3 的 `ceiling(ctxTokens)` 重算；"合计 ≈6,600 靠去重回收"改为"脊线 8,217，按阶梯预算直接装下"。
- §8 待决策项 1/3/6/7 仍然有效，但都变成新插件范围内的问题；本仓库不再改动。
- §10 的工具实验结论不变：**值 + 引用** 仍然优于 **只给引用**；预算变大不改变"宽词 scan 不可靠"的结论。

## 13. 0.2.0 范围与覆盖契约（自范围讨论文档抽取）

本节把早先的 0.2.0 范围讨论中**仍适用于 0.2** 的内容搬入本文；该文件自此只保留 0.1.5 的历史记录，不再被本文引用。0.1.5 相关条目（P0 围栏配平、R1–R5/H1–H5、发布）已全部落地并发布，不再重述；与 §12 冲突的三处标〔§12 取代〕。

### 13.1 职责划分：压缩器管 then，状态插件管 now

> **压缩器只描述"发生过什么"和"原文在哪"；"现在要做什么、做到哪一步"由 /GOAL、/plan 一类状态插件在每一轮自己供给。** 状态插件管 now，压缩器管 then，`vcc_recall` 是两者之间的桥。

这条契约同时约束两边：

| 压缩器不做 | 状态插件不依赖 |
|---|---|
| 写状态指针行、读 /plan 文件、识别 /goal 一类插件名 | 不依赖摘要内容（摘要可能把它的行删掉） |
| 把插件状态复制进摘要、出现 done/verified/success | 不依赖 tail 一定保留自己（keep-tail 是启发式） |
| 为任何 customType 写特殊代码分支 | 不把状态只存在某次工具结果里（压缩后与只读文本一样会丢） |
| 为"未解决/待办"新增推断章节 | 在 pi-vcc 被禁用或换回 Pi core 压缩时仍要能工作 |

#### 五种"非自愿接触"（现存，且已被源码确认）

| 序 | 机制 | 证据（符号） | 后果 |
|---|---|---|---|
| 1 | 注入内容会进摘要 | `before-compact.ts`：`custom_message` 经 `convertToLlm` 转成 user 内容后才 `normalize` | 每轮注入的目标文本作为 `[user]` 块反复占用 user 角色配额，而最新副本本来就在 tail 里活着 |
| 2 | `custom_message` 不占 `#N` | `global-indices.ts` 的 `isCountedMessageEntry` 只数 `type === "message"` | 同一段文本：custom 注入在摘要里没有 `(#N)`，user 角色注入才有。不对称 |
| 3 | `keep:N` 只数 `role === "user"` | `buildOwnCut` 的 `userIndices` 与 `keptUserTurns` | 若状态用 user 角色在 EOF 注入，tail 起点会落在这条注入上，真实请求被压掉，统计仍显示 `kept 1/1` |
| 4 | 重复注入污染召回 | `query` 每页 5 条 | 同文反复命中会挤掉相关条目，`touched` 重复 |
| 5 | /plan 的写文件可能不进 `[Files And Changes]` | `src/extract/files.ts` 的 `FILE_WRITE_TOOLS` 是固定名单 | 自定义写工具只能靠宿主 `fileOps` 兜底；事实层面漏记（不影响 /plan 自身，它重读文件） |

另外，`// goal:` 注解仍只是"脚本声称要做什么"的导航提示；既然状态插件才是权威，就不应让它向状态方向演化。

#### 唯一官方接触点：配置，而不是代码

`skipCustomTypes`（`src/core/settings.ts`）只在摘要输入前过滤，文档明确它**不影响**切点选择、token 校准、`firstKeptEntryId` 与 kept-user-turn 计数。因此：

- 每轮注入的状态若不想进摘要，用户把它加进 `skipCustomTypes` 即可，压缩器无需认识该插件。
- README 用一个**不带插件名**的例子说明（"per-turn injected state, e.g. a goal loop"）。
- 要"触发 turn 又不被当用户轮"用 `custom_message + triggerTurn`；要能被 recall 用普通 user 消息（占 `#N`）。取舍由插件作者决定，压缩器不替它选。

### 13.2 要删的是三个语义章节，不是一个

只删 `[Session Goal]` 会留下"声明不推断语义、却在推断状态"的契约不一致。

| 章节 | 机制 | 性质 | 中文表现 |
|---|---|---|---|
| `[Session Goal]` | `extractGoals`：`TASK_RE`/`SCOPE_CHANGE_RE` 英文动词、行级 >200 字拒绝 | 意图推断 | 长段落全空；后续改动不识别 |
| `[Outstanding Context]` | `extractOutstandingContext`：`BLOCKER_RE` + 近 20 块 + 行首需大写/反引号/引号/标识符 | **状态推断** | 基本不命中 |
| `[User Preferences]` | `extractPreferences`：`PREF_PATTERNS` 全英文、>200 字拒绝 | 偏好推断 | 基本不命中 |
| `[Files And Changes]` | 工具名白名单 + 宿主 `fileOps` | 记录的操作，不是 diff | 语言无关 |
| `[Commits]` | git 输出解析 | 事实 | 语言无关 |
| `[Tracked Commands]` | 用户配置的命令名匹配 | 事实 | 语言无关 |

两点补充：

- **`[User Preferences]` 与 AGENTS.md 重复。** Pi 每轮注入 system prompt/AGENTS.md，压缩只动消息不动系统提示；把偏好再抄进摘要，是既冗余又会过期的副本。偏好与约束的正确归宿是 AGENTS.md 或状态插件自己的持久文件。
- **`[Outstanding Context]` 比 `[Session Goal]` 更危险。** 它只读本轮窗口最后 20 块，却以"未解决"的名义呈现：旧错误不会残留，新错误可能只是暂时输出。读者会把它当成当前状态。

删除时必须同步清理四处，漏一处会得到"测试通过但行为未变"：`dedupPreferencesAgainstGoals`、goal 的 8 行 CAP、`scripts/audit-sessions.ts` 的 goal 正则、`tests/support/report.ts` 的 `SECTION_HEADERS`。

### 13.3 覆盖契约

#### 13.3.1 四个现状缺口

1. **折叠标记会整体丢范围。** `allocateTextRole` 折叠最老连续前缀时维护 `allNumeric`：被折叠候选里只要有一条 `sourceIndex` 不是数字，标记就退化为 `[N older user messages omitted]`，不再带 `#a..#b`。`custom_message` 注入的条目正好能触发这一点。
2. **legacy 省略标记从来不带 `#N`。** `capBrief`（`format.ts`）与 `capBriefToLineBudget`（`summarize.ts`）在 120 行上限处写 `...(N earlier lines omitted)`。第二次压缩后第一次的正文被挤出，只剩这句无指向的省略语。
3. **标记建议的动作不可执行。** `formatTextOmissionMarker` 生成 `scan saved history #a..#b`，但 `scan` 必须带 query；按范围读原文的调用是 `range:[a,b]`。照抄会得到参数错误。
4. **新路径本身没有忘记，但说不出还剩多少。** `buildBriefHistory` 取分支上 `firstKeptEntryId` 之前的全部消息，`compileWithEffectiveHistory` 直接把 `buildBriefCandidates(historyBlocks)` 交给分配器，不经过 `maxBlocks` 裁剪。问题不在"看不到旧内容"，而在"看不出来还有多少旧内容"。

根因是一条：**摘要是选集，没人声明它是不是封面。** 现有提示全是局部的（某条被截断、某个角色被折叠），而 agent 要判断的是全局问题："我看到的最早一条之前还有没有记录？"

#### 13.3.2 三条修正

**A. 顶部一行覆盖声明**（纯算术、零语义，约 95–150 chars）：

```text
[History] saved #2–#214; brief covers #2–#180; #181–#214 live. recall range:[2,180]
```

数据已经现成：`briefHistory.sourceIndices` 给 min/max，`firstKeptEntryId` 给 live 起点，`globalIndexById` 给最大索引。它在 `reservedChars` 里，**不参与 `headerCap` 裁剪**；顺序必须是：覆盖行 → 来源提示 → 各章节 → 正文 → note。放进 20% header 会在最窄预算下被 `trimHeaderToBudget` 从尾部整行丢弃——正好在最需要它的时候消失。

**B. 分区不变式**（比任何提示语可靠）：

```text
有效历史的所有 #N ⊆ 正文渲染的 #N ∪ 折叠标记的区间 ∪ live 区间 ∪ 显式声明的不可重建区间
```

补集非空时必须渲染 `[gap #a..#b; recall range:[a,b]]`，不允许静默。用三连压缩 fixture 直接断言 `gapCount === 0`；`coverage:{from,to,liveFrom,total}` 与 `gapCount` 落进 `details`，审计只做计数、不含正文。

**C. 范围提示要容错、要可执行：**

- `allNumeric` 不成立时不要丢掉整个范围，退化为"已引用条目的 min..max + 无引用条目数"：`[6 older user messages omitted; recall range:[3,47]; 1 without #N]`。
- 标记文本统一为真实调用：`recall range:[3,47]`；单条继续用 `(#N)`（`read`/`expand` 已验证可用）。
- `limitedReason: "edited-checkpoint"` 只有裸的 `history limited by edited checkpoint; use recall`，应带上被跳过的区间（`prefix #2–#60 not rebuilt; recall range:[2,60]`），否则它只是"有东西丢了"的模糊告警。

#### 13.3.3 分母必须先定义

以"全部保存消息"作分母，`gapCount` 会长期非零并退化成噪音：`system` 条目占 `#N` 但不渲染，`custom` 不占 `#N`，`filterNoise` 会丢弃噪声块。**分母取"有效历史消息"**（`briefHistory.messages` 的索引范围），并写进文档与 `details.coverage` 的定义。

#### 13.3.4 〔§12 取代〕legacy 路径

原讨论留了"保守不动 / 推荐补 `#N` 范围"二选一，因为它与"非 codemode 与上游逐字一致"冲突。§12.5 取消该条款后，新插件只有一条路径，这个二选一与 legacy 省略标记问题一并消失（见 §12.5 与 §5.5）。

### 13.6 未验证与风险

- **覆盖口径未验证**：覆盖行、不变式、`gapCount` 都只是设计，未验证成本，也未验证在 `charsPerToken = 2/4/6` 下的表现。
- **顶部固定成本挤压**：覆盖行 + 来源提示约 200 chars，窄预算下会挤压台账；需要一次字符扫描确认收益仍为正（§8 待决策 9）。
- **cleanup 假象**：删章节漏改审计脚本或测试报告头，会出现"测试通过但行为未变"。
- **sidecar 风险**：磁盘增长、fork 后与分支不一致、与 session 同目录的隐私边界（§12.6 已给出"派生缓存、删除无害、指纹校验"三条不变量）。
- **本讨论未运行任何测试**：所有"应"均为设计判断，不是已验证行为；0.2.0 开工前必须先补测试再改实现。
