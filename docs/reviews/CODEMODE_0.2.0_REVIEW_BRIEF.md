## 背景事实（已实测，可直接引用）

- 宿主 Pi 1.4.0 原生压缩：触发 `contextTokens > contextWindow − 16,384`；保留 `keepRecentTokens 20,000`；把被压缩前缀序列化成 `<conversation>` 单条 user 文本交给当前会话模型；输出 prose 摘要（Goal / Constraints / Progress / Decisions / Next Steps / Critical Context）；第二次起用 UPDATE prompt（摘要套摘要）。
- 一次 410,462 token 会话：原生压缩输入 210,469 token、输出 4,904、36.6s；pi-vcc 同一次压缩 0 token、28ms。
- 0.1.5 产物：6,279 chars（预算 6,287）、123 行、保留尾部 30 条（约 16,420 token）。
- 该产物：71 个变更操作只有 1 个带引用；11 个观测错误中 4 个带引用；19 对 call→result 引用语义全部正确。
- 四条件对照（原生 prose / 0.1.5 / 纯台账 / 台账+分位摘录），同尾部、同问题、同参数：用户约束命中 2/6、5/6、2/6、3/6；错误引用命中 0、5/5、5/5、4/4；当前状态四者 4/4；一个窗口外事实，原生与 0.1.5 都编造了数字，台账弃答。
- 召回补测（有工具、最多 3 次）：问题看起来可答时原生 0 次检索并编造数字；问题明显缺料时三条件都会检索（2–3 次），但"宽词 scan 命中长记录 + 只看页首"导致失败；唯一成功路径是"事实 + 引用入册"（0 次检索、答对）。
- 用户发言成本：本会话 4 条、2,478 chars；"全部保留 + 行级头尾 + 每条后第一段助手文本" = 2,332 chars。
- 优先级脊线总成本（用户发言 + 计划首段 + 契约指针 + 变更台账 + 错误/计数 + 覆盖行 + note）= 8,217 chars；旧预算 6,287 → **缺口 1,930 chars（−23%）**。

## 新决策（评审必须基于它们，不得再建议"回到 2,000 token 上限"）

1. **预算阶梯化**（建议式，可被替换）：
   ```text
   ceiling(ctx) = min(4,000, 2,000 + 0.005 × max(0, ctxTokens − 200,000))   // token
   budget = clamp(15 × blocks, 1,100, ceiling(ctx)) × charsPerToken            // UTF-16 字符
   ```
   可选精炼：`budget = min(ceiling, needed)`，`needed` 是本轮脊线的确定性成本。
2. **兼容性放开**：允许破坏与本 fork ≤0.1.5 及上游的格式兼容；可作为**独立新插件**发布（建议名 `pi-context-index`，独立版本线），旧仓库冻结在 0.1.5。
   推论：只有一条代码路径（删 legacy 与 `mergeHeaderParts`）、`details.version=3`、旧记录不迁移；两个压缩插件都注册 `session_before_compact`，**不能同时安装**。

## 仍然不可违反的硬约束

- 生产路径 0 次 LLM 调用；不得引入语义分类器、意图正则或"目标/未解决/偏好"提取。要删的是**三个**语义章节，不是一个：`[Session Goal]`（意图推断）、`[Outstanding Context]`（状态推断）、`[User Preferences]`（偏好推断，且与每轮注入的 AGENTS.md 重复）。
- 产物只允许：逐字原文（带引用）、可计数的观测事实、纯算术/结构声明；不得出现 done/verified/success，不得声称"当前状态"。
- 引用 `#N` 是会话全局消息序号，跨压缩稳定；禁止窗口相对序号。
- 同一输入字节确定，可被测试钉住；索引读取器支持 scan / read `#N`（分页）/ range / touched。
- **职责边界**：压缩器只描述"发生过什么"和"原文在哪"；"现在要做什么、做到哪一步"由状态插件每轮自给。压缩器不写状态行、不读 /plan、不识别插件名；唯一官方接触点是配置 `skipCustomTypes`。已知五种"非自愿接触"（注入内容进摘要、`custom_message` 不占 `#N`、`keep:N` 只数 user 角色、重复注入污染召回、自建写工具可能漏进 Files）必须被处理或明确声明为不处理。

## 要评审的三个核心问题

1) **可索引整个历史**：N 次压缩后仍能定位任意早期工作；引用集合单调，不因某次选集变化而丢失。
2) **不静默丢弃指针**：有效历史的每个区间要么被引用、要么被显式声明未覆盖；不允许"读者不知道还有没有更早内容"。
3) **两种首消息形态**：(a) 首条消息就是长任务书（禁令密集）；(b) 首条消息是短指令 + 一个很长的任务书文件路径（文件可随时读回，复述会形成过期副本）。

## 另需评估的场景

- 覆盖口径：以"全部保存消息"还是"有效历史消息"为分母（system 占 `#N` 不渲染、custom 不占 `#N`、噪声块被过滤）；分母错会让 `gapCount` 长期非零、退化成噪音。
- 要求的时间线：旧禁令被后来的撤销/变更指令推翻（真实发生）；零语义前提下如何表达"谁推翻谁"。
- 目标与禁令分离：禁令是行级的，字符级摘录会切掉它。
- 未验证项/验收要求：只记"做了什么"会丢"没做什么"。
- 决策反转：同一问题前后结论相反（真实发生一例，同输入重放被更正）。
- 多会话接力：压缩产物随会话结束消失，只剩文件；"目标"应持久化在哪。
- fork / retry / context-edit：位置式引用漂移；内容指纹（`#N@fp`）是否必要、成本多大。
- 极端形状：纯工具会话（全 codemode、无用户文本）与纯对话会话（无工具）。
- 超长单条工具输出（数十万字符）：如何只索引不复制。
- 敏感内容（密钥、私人数据）：是否进入索引、如何排除。
- 极窄预算（1,100 token）与上限（4,000 token）两端各保留/删除什么；覆盖行 + 来源提示约 200 chars 的顶部固定成本在窄预算下是否仍为正收益。
- 预算摊销：摘要每轮都被发送；阶梯预算多出的 token 是否值得，如何用实验证明。
- 旁挂索引（sidecar）：可重建性、fork 一致性、磁盘与隐私；`view` 记录"显示了什么/隐藏了什么"能否从结构上保证指针不静默丢失。

## 第一性原理要求（按此顺序推理）

1. 先定义产物用途：谁读、读后要做什么、失败代价是什么；据此列出"必须能回答的问题清单"。
2. 用信息论/期望收益下界论证：预算从 6,287 涨到 9,588 是否值得；给出"每个 token 换回的可核查事实"的度量方式（必须可测）。
3. 推导不可省略的不变量（分区覆盖、单调性、可校验性、确定性、可重建性），每条给出可自动测试的断言。
4. 给出最小数据结构（字段级），说明每个字段被谁使用、失效时如何表现。
5. 给出预算分配公式（区分两种首消息形态与 `needed` 精炼），在 200K/300K/410K/500K 四个规模上各算一遍。
6. 给出失效模式清单与反证实验，包括"读者不点指针""模型对空缺编号""预算变大后被无关内容占满""删掉 sidecar 后视图变化"。
7. 明确指出本文档中你认为应当删除的设计。

## 输出格式

1. 结论（≤10 行）
2. 用途与"必须可回答的问题"清单
3. 预算与信息论论证（含 6,287→9,588 的收益/成本判断）
4. 不变量与可测断言
5. 最小数据结构（字段表，含 sidecar 取舍）
6. 预算分配公式 + 四档算例

9. 你不同意本文档的 3 点（理由 + 替代方案）
10. 你认为应当删除的 1–2 个设计
11. 未知与风险

## 反模式（不要给这些建议）

- 引入 LLM/语义分类器/意图正则来写"目标/待办/未解决"；只删 `[Session Goal]` 而留下 `[Outstanding Context]`。
- 用"更强的提醒语"代替结构约束；无条件打印固定提醒。
- 按重要性评分排序（会打乱时间线）；把标记同时用于"截断/折叠/不可重建"三种含义。
- 复述任务书文件内容（形成第二个可能过期的副本）。
- 只给引用不给值（读者要翻 19K 字符记录才能拿到一个计数）。
- 用"预算不够就压缩内容"解决覆盖问题；预算已按阶梯放开，问题转为"按什么顺序花"。
- 让压缩器认识具体状态插件，或建议把两个压缩插件同时安装。
- 保留 legacy 路径做"逐字兼容"（已明确取消）。
